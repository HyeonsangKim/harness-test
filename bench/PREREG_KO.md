# 사전 등록: 하네스 v0 A/B 시험

각 절 제목의 시각은 그 절을 추가한 git 커밋의 시각이다(2026-10-21, 한국 시간).

평가 과제(eval)를 돌리기 전에 이 문서와 코드를 커밋한다. 결과를 본 뒤에 과제, 채점, 조건, 통계 방법을 바꾸지 않는다. 바꿔야 하면 새 버전으로 다시 등록하고 처음부터 다시 돌린다.

## 질문

같은 모델, 같은 과제, 같은 도구에서 하네스 v0(`hx.py`의 기능 7개)를 켜면 업무 성공률이 오르는가? 오른다면 그것이 "한 번 더 묻기" 때문이 아니라 하네스가 주는 구체적인 신호 때문인가?

## 조건

| 조건 | 내용 |

| C | B + 첫 답 뒤에 "다시 확인하고 답해 달라"를 한 번 묻는다. 구체적 정보 없이 턴만 하나 더 주는 대조군 |

- 실행 순서는 고정 시드(7)로 섞어서, 서버 상태 변화가 세 조건에 고르게 걸리게 한다.

## 과제

`tasks.py`의 eval 30개: ERP 14, 코드 8, 문서 8.

- 하네스 코드를 보지 못하게 막은 별도 작성자가 `env.py`와 `grade.py`만 보고 썼다.
- 정답은 데이터에서 코드로 계산한다.
- 각 과제는 세 가지를 자체 검증했다.
  - 정답 예시는 통과한다.
  - 그럴듯한 오답은 실패한다.
  - 코드 과제는 고치기 전 상태와 테스트를 바꿔치기한 상태가 실패한다.
- dev 8개는 하네스 점검용이며 효과 주장에 쓰지 않는다.

## 채점

- 과제의 `check` 함수로만 채점한다. 사람 판단은 없다.
- 형식이 아니라 내용을 본다. 숫자의 쉼표와 "원", 코드블록 감싸기 등은 허용한다.
- 코드 과제는 원래 테스트를 복원해서 돌리고, 숨긴 테스트도 함께 돌린다.

## 지표와 통계

- **주 지표:** 실행 단위 성공률. H와 B의 차이.
- **보조 지표:** pass^k(한 과제를 k번 돌려 k번 다 성공한 비율, τ-bench 정의). 그리고 H와 C의 차이.
- **통계:**
  - 과제 단위로 짝을 지은 차이의 평균과 부트스트랩 95% 신뢰구간(과제 재표본 1만 번, 시드 0).
  - 과제 단위 부호 검정(정확 이항).
  - 실행 단위 McNemar 정확 검정.
- **"좋아졌다"의 판정:** H − B의 95% 신뢰구간 하한이 0보다 크면 개선이다. 하한이 0 이하면 "차이를 확인하지 못함"으로 보고한다.
- **제외 규칙:** 게이트웨이·네트워크 오류(`http_`, `connection`)로 끝난 실행만 점수에서 빼고 다시 돌린다. 뺀 건수는 보고한다. 모델이 만든 실패(턴 초과, 형식 오류 등)는 실패로 센다.

## 실행 순서 보완 (커밋 eba55e1, 09:55, 평가 결과 분석 전)

- **바꾼 것:** 실행 순서만 바꿨다. 무작위로 섞은 뒤 회차(rep) 순으로 정렬한다. 1회차의 30과제 × 3조건을 전부 끝낸 뒤 2회차로 넘어간다.

- **환경:** 사외 Mac, 서버 설정은 위와 같다. TAT-QA 공식 채점이 numpy·pandas·scipy를 쓰므로, 실행기는 그것들이 설치된 별도 가상환경의 파이썬으로 돌린다. 하네스 코드는 그대로 표준 라이브러리만 쓴다.

## RT2(조건부 바로 끝내기)와 자동 조정 제한값 등록 (RT2 실행 전)

**RT2 = RT + `crosscheck`:**
- 코드 출력이 답 형식을 통과해도 바로 끝내지 않는다. 대신 "다른 방법으로 같은 값을 계산하는 독립 프로그램"을 한 번 더 요청한다.
- 두 답이 같으면(숫자는 소수 6자리 반올림, 목록은 정렬 후 비교) 바로 끝낸다.
- 다르면 두 값을 보여 주고 "요청의 규칙을 하나씩 대조해 고쳐 답하라"고 한 뒤, 이후에는 바로 끝내기를 쓰지 않는다.
- 두 번째 코드가 첫 번째와 똑같으면 대조로 치지 않고 다른 방법을 다시 요구한다.
- 근거: PAL(arXiv 2211.10435)의 프로그램 다수결, Jev 리포트의 "확신이 있을 때만 위임" 원칙.
- 설계 출처: `tasks_notool2.py`의 RT 오답(13건 중 10건이 바로 끝내기로 끝남)을 보고 만들었다. 그래서 공개 벤치마크(`tasks_bench.py`)에서 검증한다.
- 판정: RT2 − RT 하한 > 0이면 채택한다. 토큰과 시간 비율도 보고한다.

**자동 조정 제한값 (모델별 설정 없이):**
- **출력 상한:** 응답이 출력 상한에 걸려 내용 없이 끝나면 상한을 두 배로 올려 다시 묻는다(최대 32768, 이벤트 `length_retry`).
- **코드 실행 시간 상한:** 20초 + 넘겨받은 자료 1MB당 10초. `LLM_PY_TIMEOUT`으로 덮어쓸 수 있다.
- **코드 출력 상한:** 4,000자 그대로. 넘치면 앞 1/3과 뒤 2/3를 남기고 "N자 생략, 필요한 값만 출력하라"는 안내를 넣는다(전에는 뒤 4,000자만 남겼다). `LLM_PY_OUTPUT`으로 덮어쓸 수 있다.
- **`finish_line` 수정:** 실행 결과 뒤에 하네스 안내(정체 감지 등)가 붙어도 결과 JSON을 읽는다. 전에는 안내가 붙으면 바로 끝내기가 걸리지 않았다.
- 이 변경들은 진행 중인 벤치마크 P·RT·PT 실행(이미 시작된 프로세스)에는 적용되지 않는다. RT2 실행부터 적용된다.

## 결함 주입 시험 등록 (실행 전)

## 공개 벤치마크 표본 축소 (결과 32건 시점)

- 처리량이 예상보다 낮다. 사고 모드, RT2, 결함 주입이 동시에 돌아 한 건에 4~8분이 걸린다. 그래서 TAT-QA와 GSM-Hard를 각 100문항에서 50문항으로 줄인다.

- 표본이 줄어 신뢰구간이 넓어진다. RT−P처럼 큰 차이는 판정할 수 있다. RT2−RT처럼 작은 차이는 "판정 불가"로 끝날 수 있다.

## TAT-QA 질문 문구 수정과 재실행

- **실수:** 질문 문구가 "scale이 가리키는 단위로 답하라"여서, 모델이 단위를 바꿔 답해도 된다고 읽을 수 있었다. 공식 채점은 표의 단위 그대로의 답을 기대하고, 숫자를 소수 둘째 자리에서 반올림한 뒤 단위를 곱한다. 그래서 값이 같은 답(−6.216 million = −6,216 thousand)이 오답이 됐다. 중간 점검에서 발견했다.
- **수정:** "보고서가 쓰는 단위를 그대로 유지하고 바꾸지 마라. 천 단위 표면 천 단위로(예: 1234, thousand). 퍼센트는 퍼센트 값으로"를 넣었다. 예시 숫자는 데이터에 없는 값으로 골랐다. 정답 예시는 여전히 100/100 통과한다.
- **조치:** TAT-QA 결과(P, PT, RT, RT2 합계 15건)는 모두 버리고 처음부터 다시 돌린다. GSM-Hard 결과는 문구가 바뀌지 않았으므로 유지한다.
- **GSM-Hard 데이터 잡음:** 정답이 비현실적인 문항이 있다(예: 사람 수 1345.567). 데이터 결함으로 알려져 있다. 모든 조건에 똑같이 적용되므로 주 분석은 그대로 한다. "정답이 정수여야 하는데 정수가 아닌 문항"을 뺀 민감도 분석을 사후 분석으로 따로 보고한다.

## 표 정규화 판(RT4) 등록 (실행 전)

- **변경 (RT 대비 이것만):** 표 파일을 만드는 방식.
  - 숫자 안의 쉼표(1,234)는 구분자로 세지 않는다. 탭이나 `|` 표로 잡힌 줄은 쉼표 표로 다시 잡지 않는다. 결함 주입 과제에서 탭 표의 금액 쉼표 때문에 가짜 쉼표 표가 여러 개 생기는 것을 실행 전 점검에서 확인했다.
  - 칸 공백 제거, 바깥 `|`와 마크다운 정렬 줄 제거.
  - 머리글 여러 줄을 열마다 하나의 이름으로 합친다(위 줄의 묶음 이름은 오른쪽 빈 칸으로 이어 붙인다. 예: "1분기 매출"). 빈 이름은 col1, col2…, 중복 이름은 번호를 붙인다.
  - 모두 쉼표 구분 CSV(따옴표 처리)로 쓴다.
  - 스킬 문서는 RT와 같은 `python_v3.md`를 쓴다.
- **적용 범위:** 표가 있는 과제만 돌린다. TAT-QA 50문항, 결함 주입 24개. GSM-Hard 50문항에는 추출되는 표가 0개라 RT4와 RT가 같은 조건이므로 돌리지 않는다.
- **비교:** 같은 과제 전체에서 RT4 − RT 짝 비교(틀린 문항만 다시 돌리지 않는다). 결함 주입은 RT를 24개 모두 채운 뒤 비교한다.
- **판정:** 정확도 차이의 95% 신뢰구간과 토큰 비율(입력·출력 따로)을 보고한다. 정확도 하한 > −10%p(비열등)이고 토큰이 줄면 RT4를 최종으로 바꾼다. 표본이 작아 "판정 불가"로 끝날 수 있다.

## GSM-Hard 정답 오류 처리 규칙 (본 실행 결과 집계 전)

- 숫자 비교만으로 거르는 규칙은 오탐이 많아(50문항 중 20개, 예: 5%를 0.05로 쓴 경우) 쓰지 않는다.
- 하네스 실행 기록을 보지 않는 별도 에이전트가 50문항을 질문만 보고 다시 풀고, 정답과 다른 문항을 "정답 오류 / 해석이 둘 / 자기 실수"로 분류한다. 정답 오류와 해석이 둘인 문항은 사람이 원문을 보고 확정한다.
- **주 분석:** 원래 정답 그대로. **민감도 분석:** 확정된 정답 오류 문항을 모든 조건에서 똑같이 빼고 다시 집계한다. 모델 답은 다시 돌리지 않는다.
- 앞 절의 "정답이 정수가 아닌 문항 제외" 계획은 이 규칙으로 대체한다.
- **확정 (본 실행 결과 집계 전):** 50문항 중 15개가 정답 오류다(`gsmhard_label_errors.txt`, 근거는 `gsmhard_label_audit.json`). 모두 참조 프로그램이 원래 GSM8K 숫자를 바꾸지 않은 채 남겨 둔 경우다(예: 질문은 "1793815일", 프로그램은 3일). 15개 중 7개를 사람이 원문과 대조해 확인했다. 해석이 둘인 문항은 없었다.

- **판정 (주 질문): RT4가 사고 모드(PT)보다 정확한가?**
  - 100문항 전체에서 RT4 − PT의 95% 하한이 0보다 크면 "더 정확하다"고 쓴다.
  - 하한이 −10%p보다 크면 "같은 수준"이라고 쓴다.
  - 토큰(입력·출력 따로)과 시간 비율을 함께 보고한다.
- **오류 처리:** 연결이나 서버 오류는 주 분석에서 빼고, 민감도 분석에서는 틀림으로 친다(앞 실행과 같다).

## RT5 등록과 재대결 조건 추가 (재대결 시작 전)

- **발견 (결함 주입 중간 점검):** RT4는 표를 쉼표 CSV로 바꿔 저장한다. 그런데 질문에 "탭으로 구분"이라고 적혀 있으면, 모델이 도구 설명을 무시하고 `delimiter='\t'`로 읽다가 실패해 턴을 버렸다.
  - 결함 주입 4개(mx_01, mx_04, mx_06, mx_19), TAT-QA 6개 실행 기록에서 같은 행동이 보였다.
  - mx_01, mx_03은 RT가 맞히고 RT4가 틀렸다.
- **RT5 (RT4 대비 이것만):** 탭 표는 정규화한 뒤에도 탭 구분으로 저장한다. 쉼표 표와 `|` 표는 RT4와 같이 쉼표 CSV로 저장한다. 도구 설명에 표마다 구분자를 적는다.
- **재대결 조건:** P, PT, RT, RT4, RT5. 재대결 실행은 아직 시작하지 않았다.
  - **주 판정:** 등록대로 RT4 − PT다.
  - **부 판정:** RT5 − PT와 RT5 − RT4를 같은 기준으로 보고한다. RT5는 결함 주입 중간 기록을 보고 만든 것이고, 재대결 문항은 보지 않았다.
  - **최종판 결정:** 재대결과 결함 주입에서 RT5가 RT4보다 정확도 하한 −10%p 이상(비열등)이고 토큰이 늘지 않으면 RT5를 최종판으로 한다.
- **개발 문항 확인:** 재대결 뒤 RT5를 TAT-QA 앞 50문항과 결함 주입 24개에서도 돌린다.
