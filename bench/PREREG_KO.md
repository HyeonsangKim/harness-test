# 사전 등록: 하네스 v0 A/B 시험

각 절 제목의 시각은 그 절을 추가한 git 커밋의 시각이다(2026-10-21, 한국 시간).

평가 과제(eval)를 돌리기 전에 이 문서와 코드를 커밋한다. 결과를 본 뒤에 과제, 채점, 조건, 통계 방법을 바꾸지 않는다. 바꿔야 하면 새 버전으로 다시 등록하고 처음부터 다시 돌린다.

## 질문

같은 모델, 같은 과제, 같은 도구에서 하네스 v0(`hx.py`의 기능 7개)를 켜면 업무 성공률이 오르는가? 오른다면 그것이 "한 번 더 묻기" 때문이 아니라 하네스가 주는 구체적인 신호 때문인가?

## 조건

| 조건 | 내용 |

| C | B + 첫 답 뒤에 "다시 확인하고 답해 달라"를 한 번 묻는다. 구체적 정보 없이 턴만 하나 더 주는 대조군 |

- 실행 순서는 고정 시드(7)로 섞어서, 서버 상태 변화가 세 조건에 고르게 걸리게 한다.

## 과제

`tasks.py`의 eval 30개: ERP 14, 코드 8, 문서 8.

- 하네스 코드를 보지 못하게 막은 별도 작성자가 `env.py`와 `grade.py`만 보고 썼다.
- 정답은 데이터에서 코드로 계산한다.
- 각 과제는 세 가지를 자체 검증했다.
  - 정답 예시는 통과한다.
  - 그럴듯한 오답은 실패한다.
  - 코드 과제는 고치기 전 상태와 테스트를 바꿔치기한 상태가 실패한다.
- dev 8개는 하네스 점검용이며 효과 주장에 쓰지 않는다.

## 채점

- 과제의 `check` 함수로만 채점한다. 사람 판단은 없다.
- 형식이 아니라 내용을 본다. 숫자의 쉼표와 "원", 코드블록 감싸기 등은 허용한다.
- 코드 과제는 원래 테스트를 복원해서 돌리고, 숨긴 테스트도 함께 돌린다.

## 지표와 통계

- **주 지표:** 실행 단위 성공률. H와 B의 차이.
- **보조 지표:** pass^k(한 과제를 k번 돌려 k번 다 성공한 비율, τ-bench 정의). 그리고 H와 C의 차이.
- **통계:**
  - 과제 단위로 짝을 지은 차이의 평균과 부트스트랩 95% 신뢰구간(과제 재표본 1만 번, 시드 0).
  - 과제 단위 부호 검정(정확 이항).
  - 실행 단위 McNemar 정확 검정.
- **"좋아졌다"의 판정:** H − B의 95% 신뢰구간 하한이 0보다 크면 개선이다. 하한이 0 이하면 "차이를 확인하지 못함"으로 보고한다.
- **제외 규칙:** 게이트웨이·네트워크 오류(`http_`, `connection`)로 끝난 실행만 점수에서 빼고 다시 돌린다. 뺀 건수는 보고한다. 모델이 만든 실패(턴 초과, 형식 오류 등)는 실패로 센다.

## 실행 순서 보완 (커밋 eba55e1, 09:55, 평가 결과 분석 전)

- **바꾼 것:** 실행 순서만 바꿨다. 무작위로 섞은 뒤 회차(rep) 순으로 정렬한다. 1회차의 30과제 × 3조건을 전부 끝낸 뒤 2회차로 넘어간다.

- **환경:** 사외 Mac, 서버 설정은 위와 같다. TAT-QA 공식 채점이 numpy·pandas·scipy를 쓰므로, 실행기는 그것들이 설치된 별도 가상환경의 파이썬으로 돌린다. 하네스 코드는 그대로 표준 라이브러리만 쓴다.

## RT2(조건부 바로 끝내기)와 자동 조정 제한값 등록 (RT2 실행 전)

**RT2 = RT + `crosscheck`:**
- 코드 출력이 답 형식을 통과해도 바로 끝내지 않는다. 대신 "다른 방법으로 같은 값을 계산하는 독립 프로그램"을 한 번 더 요청한다.
- 두 답이 같으면(숫자는 소수 6자리 반올림, 목록은 정렬 후 비교) 바로 끝낸다.
- 다르면 두 값을 보여 주고 "요청의 규칙을 하나씩 대조해 고쳐 답하라"고 한 뒤, 이후에는 바로 끝내기를 쓰지 않는다.
- 두 번째 코드가 첫 번째와 똑같으면 대조로 치지 않고 다른 방법을 다시 요구한다.
- 근거: PAL(arXiv 2211.10435)의 프로그램 다수결, Jev 리포트의 "확신이 있을 때만 위임" 원칙.
- 설계 출처: `tasks_notool2.py`의 RT 오답(13건 중 10건이 바로 끝내기로 끝남)을 보고 만들었다. 그래서 공개 벤치마크(`tasks_bench.py`)에서 검증한다.
- 판정: RT2 − RT 하한 > 0이면 채택한다. 토큰과 시간 비율도 보고한다.

**자동 조정 제한값 (모델별 설정 없이):**
- **출력 상한:** 응답이 출력 상한에 걸려 내용 없이 끝나면 상한을 두 배로 올려 다시 묻는다(최대 32768, 이벤트 `length_retry`).
- **코드 실행 시간 상한:** 20초 + 넘겨받은 자료 1MB당 10초. `LLM_PY_TIMEOUT`으로 덮어쓸 수 있다.
- **코드 출력 상한:** 4,000자 그대로. 넘치면 앞 1/3과 뒤 2/3를 남기고 "N자 생략, 필요한 값만 출력하라"는 안내를 넣는다(전에는 뒤 4,000자만 남겼다). `LLM_PY_OUTPUT`으로 덮어쓸 수 있다.
- **`finish_line` 수정:** 실행 결과 뒤에 하네스 안내(정체 감지 등)가 붙어도 결과 JSON을 읽는다. 전에는 안내가 붙으면 바로 끝내기가 걸리지 않았다.
- 이 변경들은 진행 중인 벤치마크 P·RT·PT 실행(이미 시작된 프로세스)에는 적용되지 않는다. RT2 실행부터 적용된다.

## 결함 주입 시험 등록 (실행 전)

- **과제:** `tasks_messy.py` 24개. 지저분한 실제형 자료 8유형 × 3개다.

## 공개 벤치마크 표본 축소 (결과 32건 시점)

- 처리량이 예상보다 낮다. 사고 모드, RT2, 결함 주입이 동시에 돌아 한 건에 4~8분이 걸린다. 그래서 TAT-QA와 GSM-Hard를 각 100문항에서 50문항으로 줄인다.

- 표본이 줄어 신뢰구간이 넓어진다. RT−P처럼 큰 차이는 판정할 수 있다. RT2−RT처럼 작은 차이는 "판정 불가"로 끝날 수 있다.

## TAT-QA 질문 문구 수정과 재실행

- **실수:** 질문 문구가 "scale이 가리키는 단위로 답하라"여서, 모델이 단위를 바꿔 답해도 된다고 읽을 수 있었다. 공식 채점은 표의 단위 그대로의 답을 기대하고, 숫자를 소수 둘째 자리에서 반올림한 뒤 단위를 곱한다. 그래서 값이 같은 답(−6.216 million = −6,216 thousand)이 오답이 됐다. 중간 점검에서 발견했다.
- **수정:** "보고서가 쓰는 단위를 그대로 유지하고 바꾸지 마라. 천 단위 표면 천 단위로(예: 1234, thousand). 퍼센트는 퍼센트 값으로"를 넣었다. 예시 숫자는 데이터에 없는 값으로 골랐다. 정답 예시는 여전히 100/100 통과한다.
- **조치:** TAT-QA 결과(P, PT, RT, RT2 합계 15건)는 모두 버리고 처음부터 다시 돌린다. GSM-Hard 결과는 문구가 바뀌지 않았으므로 유지한다.
- **GSM-Hard 데이터 잡음:** 정답이 비현실적인 문항이 있다(예: 사람 수 1345.567). 데이터 결함으로 알려져 있다. 모든 조건에 똑같이 적용되므로 주 분석은 그대로 한다. "정답이 정수여야 하는데 정수가 아닌 문항"을 뺀 민감도 분석을 사후 분석으로 따로 보고한다.

## 표 정규화 판(RT4) 등록 (실행 전)

- **변경 (RT 대비 이것만):** 표 파일을 만드는 방식.
  - 숫자 안의 쉼표(1,234)는 구분자로 세지 않는다. 탭이나 `|` 표로 잡힌 줄은 쉼표 표로 다시 잡지 않는다. 결함 주입 과제에서 탭 표의 금액 쉼표 때문에 가짜 쉼표 표가 여러 개 생기는 것을 실행 전 점검에서 확인했다.
  - 칸 공백 제거, 바깥 `|`와 마크다운 정렬 줄 제거.
  - 머리글 여러 줄을 열마다 하나의 이름으로 합친다(위 줄의 묶음 이름은 오른쪽 빈 칸으로 이어 붙인다. 예: "1분기 매출"). 빈 이름은 col1, col2…, 중복 이름은 번호를 붙인다.
  - 모두 쉼표 구분 CSV(따옴표 처리)로 쓴다.
  - 스킬 문서는 RT와 같은 `python_v3.md`를 쓴다.
- **적용 범위:** 표가 있는 과제만 돌린다. TAT-QA 50문항, 결함 주입 24개. GSM-Hard 50문항에는 추출되는 표가 0개라 RT4와 RT가 같은 조건이므로 돌리지 않는다.
- **비교:** 같은 과제 전체에서 RT4 − RT 짝 비교(틀린 문항만 다시 돌리지 않는다). 결함 주입은 RT를 24개 모두 채운 뒤 비교한다.
- **판정:** 정확도 차이의 95% 신뢰구간과 토큰 비율(입력·출력 따로)을 보고한다. 정확도 하한 > −10%p(비열등)이고 토큰이 줄면 RT4를 최종으로 바꾼다. 표본이 작아 "판정 불가"로 끝날 수 있다.

- 숫자 비교만으로 거르는 규칙은 오탐이 많아(50문항 중 20개, 예: 5%를 0.05로 쓴 경우) 쓰지 않는다.
- 하네스 실행 기록을 보지 않는 별도 에이전트가 50문항을 질문만 보고 다시 풀고, 정답과 다른 문항을 "정답 오류 / 해석이 둘 / 자기 실수"로 분류한다. 정답 오류와 해석이 둘인 문항은 원문을 보고 확정한다(실제로는 메인 세션 Claude가 확인했다).
- **주 분석:** 원래 정답 그대로. **민감도 분석:** 확정된 정답 오류 문항을 모든 조건에서 똑같이 빼고 다시 집계한다. 모델 답은 다시 돌리지 않는다.
- 앞 절의 "정답이 정수가 아닌 문항 제외" 계획은 이 규칙으로 대체한다.
- **확정 (본 실행 결과 집계 전):** 50문항 중 15개가 정답 오류다(`gsmhard_label_errors.txt`, 근거는 `gsmhard_label_audit.json`). 모두 참조 프로그램이 원래 GSM8K 숫자를 바꾸지 않은 채 남겨 둔 경우다(예: 질문은 "1793815일", 프로그램은 3일). 15개 중 7개를 메인 세션(Claude)이 원문과 대조해 확인했다(정정: 처음에 "사람이"라고 잘못 적었다. 사람은 확인하지 않았다). 해석이 둘인 문항은 없었다.

     - 자유 질문이라도 숫자가 3개 이상 있고 "합계·평균·얼마·비율·how many·average…" 같은 계산 요구가 있으면 하네스를 켠다. IFEval 150문항 중 1문항만 새로 켜진다.
     - 코드 작성 요청(답 형식이 글이고 코드를 요구)은 가벼운 코드 규칙(`python_code.md`)으로 보낸다. 내용은 "예시로 한 번 돌려 볼 수 있다, 그다음 코드 블록 하나로 답한다"이고, 코드 강제·빈 칸 확인은 없다.
- **RT13 개발 시험 중단:** RT16에 RT13의 내용이 모두 들어 있다.
- **개발 시험:** RT16을 재대결 2 문항 200개, 결함 주입 24개, 업무 과제(`tasks_notool2`) 30개, HumanEval+ 163개에서 1회씩 돌린다.
- **재대결 3 판 선택:** 앞의 규칙(개발 문항 PT 대비 점추정 최대)에 RT16을 후보로 더한다. 후보는 RT12, RT14, RT15, RT16이다.
  - RT14가 RT12보다 나으면 RT16에 사고를 켠 RT16T도 개발 문항에서 돌리고 후보에 넣는다.
  - 결함 주입·업무 과제·HumanEval+에서 RT12/RT9 대비 −10%p보다 나빠지는 판은 후보에서 뺀다.
- **RT15(B) 개발 시험 중단:** 서버를 다섯 실행이 나눠 써서 재대결 3 PT가 너무 느리다. 후보 중 사전 근거가 가장 약한 B를 멈춘다(6/200건 시점, 중간 결과를 보고 내린 결정이 아님). 후보는 RT12, RT14, RT16이다.

## 표 추출기 v2와 RT17·RT18 (개발 시험 전)

- **발견 (MultiHiertt 연결 중):** 기존 추출기는 첫 줄이 "Years Ended December 31,"처럼 여러 칸에 걸친 묶음 머리글인 표를 표로 인식하지 못했다. 이름 붙은 칸이 2개 미만이기 때문이다.
  - 재대결 2의 TAT-QA 100문항 중 53문항에서 표 파일이 하나도 만들어지지 않았다. 모델은 input.txt를 직접 잘라 읽어야 했다.
- **추출기 v2 (`extract_tables(clean="v2")`, `python_tool(clean_tables="keep2")`):**
  - 머리글은 첫 세 줄을 함께 보고 판단한다. 숫자 칸은 빼고 본다. 이름 칸 길이는 80자까지 허용한다.
  - 2열 탭 표를 허용한다.
  - 같은 열 수의 표가 메모·빈 줄 2줄 이내로 끊겼으면 하나로 이어 붙인다. 끊긴 조각의 첫 데이터 행이 머리글로 읽히는 것을 막기 위해서다.
  - **효과 (모델 없이 측정):** 재대결 2 TAT-QA에서 표 0개 문항이 53 → 2로 줄었다. MultiHiertt 표 추출은 319 → 557/601개로 늘었다. 결함 주입에서 표 0개 과제는 6 → 4다.
  - **알려진 한계:** 한 표 안에 머리글 블록이 두 번 나오면 두 번째 블록의 머리글이 데이터 행에 섞인다.
- **RT17 = RT12 + 추출기 v2**(효과 분리용), **RT18 = RT16 + 추출기 v2**.
- **개발 시험:**
  - RT17은 재대결 2 TAT-QA 100문항에서 먼저 돌리고, 이어서 결함 주입 24개에서 돌린다. GSM-Hard에는 표가 없어 RT12와 같다.
  - RT18은 RT16 개발 결과를 본 뒤 결정한다.
- **재대결 3 후보:** RT17과 RT18을 더한다. 선택 규칙은 그대로다.
- **RT16 개발 시험 일시 중지 (11/200건):** 서버를 네 실행이 나눠 써서 모두 느리다. 가장 큰 원인(표 미추출)을 겨냥한 RT17을 우선한다. RT16의 내용은 RT18(= RT16 + 추출기 v2)로 RT17 결과 뒤에 잰다. 중간 결과를 보고 내린 결정이 아니라 서버 시간 배분이다.

## 어려운 업무 시험 등록 (실행 전)

- **목적:** 짧은 표 하나·계산 한두 번인 과제에서는 사고 모드도 잘 풀어 차이가 나지 않는다. 실제 사내 업무처럼 긴 표·여러 표·다단계 규칙·지저분한 자료에서 하네스가 사고 모드보다 나은지 본다.
- **과제:**
  1. **`tasks_hard_ko.py` (60개, split `hard_ko`):** 하네스 코드를 보지 못한 작성자가 만들었다.
     - 영역: 회계, 인사·급여, 구매·재고, 영업, 총무, 법무
     - 행 122~464, 표·목록 1~4개, 규칙 3~9단계
     - 섞인 것: 중복, 소계, 단위 혼재, 한글 금액, 날짜 형식 혼재, 정정 행, 모순
     - 자체 검증: 정답 풀이 60/60 통과, 그럴듯한 오답 2~5개씩 모두 탈락
     - 판단 규칙상 60개 모두 하네스가 켜진다. 정리 규칙 단서가 잡히는 과제는 44개다.
  2. **`tasks_hard.py` MultiHiertt (150문항, split `hard`):** ACL 2022, MIT. dev 산술 문항 중 근거 표가 2개 이상이거나 15행 이상인 문항이다(시드 0). 공식 수치 비교 규칙(상대 0.1%, 절댓값 0.1 상한)을 쓰되, 음수 부호를 지우는 공식 코드의 동작은 따르지 않는다.
- **알려진 한계 (실행 전 점검):**
  - hard_ko의 기록 상당수는 구분자 표가 아니라 글 형식 목록이라 표 파일이 생기지 않는다. 모델이 input.txt를 직접 읽어야 한다.
  - 쉼표가 빠진 행을 일부러 넣은 CSV는 추출기 v2에서도 여러 조각으로 나뉜다(hk_43).
  - 이번 시험을 위해 추출기를 더 고치지 않는다.
- **조건:** P, PT(흘려받기), 재대결 3에서 고른 최종 하네스 판. 각 1회.
- **판정:** 최종 하네스 − PT의 95% 하한 > 0이면 "어려운 업무에서 사고 모드보다 정확하다"고 쓴다. 정확도와 함께 토큰·시간 비율을 보고한다.
- **순서:** P는 판과 무관하므로 먼저 돌린다. PT와 하네스는 재대결 3 판정 뒤에 돌린다.

## RT19 = RT14 + 추출기 v2 (등록, 개발 시험 전)

- **근거 (개발 TAT-QA, 같은 문항에서 맞힌 수):**
  - RT14 37문항: PT 32, RT12 27, RT14 32
  - RT17 36문항: PT 31, RT12 26, RT17 27
  - 사고 모드에 지는 원인(질문 읽기)을 메운 것은 사고를 켠 RT14이고, 추출기 v2만으로는 격차가 줄지 않았다.
  - 추출기 v2는 여러 표 문서에서 표를 훨씬 많이 잡는다(MultiHiertt 319 → 557/601개).
- **RT19:** RT14(빈 칸 확인, 작업 규칙 v5, 사고 켬, 흘려받기)에 추출기 v2(`keep2`)를 더한다.
- **개발 시험:** 재대결 2 TAT-QA 100문항에서 1회 돌린다.
- **재대결 3 후보:** 후보에 더한다. 선택 규칙은 그대로다(개발 문항 PT 대비 점추정 최대).
- **어려운 업무 시험:** 재대결 3에서 고른 판과 함께 RT19도 돌린다. 여러 표 문서에서 추출기 v2의 효과를 보기 위해서다.
- **RT17 개발 시험 중단 (40/100건):** 같은 문항에서 PT 31, RT12 26, RT17 27이다(36문항). 추출기 v2만으로는 PT와의 격차가 줄지 않는다는 결론이 분명하다. 추출기 효과는 RT19에서 함께 본다. 서버 자리 3개를 재대결 3과 RT14·RT19에 돌린다. RT17은 재대결 3 후보에서 뺀다.
- **RT14 개발 시험 중단 (42/100건):** 사고를 켜면 질문 읽기 격차가 메워진다는 목적은 확인됐다(같은 37문항에서 PT 32, RT12 27, RT14 32). RT19가 RT14를 포함하므로, TAT-QA 개발을 끝까지 돌리면 거의 같은 것을 두 번 재게 된다. 재대결 3 후보는 RT19와 RT12로 좁힌다. RT19가 개발 문항에서 RT14의 42건보다 뚜렷이 나쁘면 RT14 결과를 다시 검토한다.
