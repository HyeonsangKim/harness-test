1. 작은 코어란

코어는 어떤 업무를 시키든 똑같이 필요한 부분이다. 모델에게 요청을 보내고, 응답에서 "무엇을 하려는지" 읽어내고, 도구를 실행시켜 결과를 돌려주고, 예산을 지키고, 모든 것을 기록한다. "작다"는 것은 여기에 업무 규칙, 특정 모델 전용 처리, 외부 프레임워크가 하나도 들어가지 않는다는 뜻이다.

그림 1. 전체 구조. 파란 점선 안이 코어다. 초록(업무)과 주황(모델)은 바꿔 끼우는 부품이다.

코어에 들어가는 것과 들어가지 않는 것

왜 작게 만드나

  • 사내 결과는 밖으로 가져올 수 없다. 코드는 git clone으로 들어가지만 결과는 화면 요약을 손으로 옮겨 온다. 패키지 설치가 어려울 수 있어 표준 라이브러리만 쓰고 짧게 쓴다. v1 전체(코어+첫 업무 어댑터) 목표는 약 530~750줄(추정)이다.
  • 작아야 검증이 끝까지 된다. 사외에서 가짜 서버로 모든 분기를 시험한 뒤 들여갈 수 있다.
  • 업계 근거. 최근 하네스들이 "작은 공통 루프 + 바깥 부품" 구조로 수렴하고 있다. mini-SWE-agent는 약 100줄 루프로 높은 성능을 냈다고 밝힌다(모델·날짜 미표기). 복잡한 루프보다 좋은 부품과 좋은 기록이 중요하다는 쪽이다.

업무 하나가 코어를 지나가는 흐름

그림 2. 업무 한 건의 흐름. 파란 칸은 코어가, 초록 칸은 업무 어댑터가 맡는다. 코어는 "무엇을" 검사·채점하는지 모르고, 어댑터에 맡길 "때"만 안다.

실행 중 검사(⑥)와 사후 채점(⑦)을 나누는 이유: ⑥은 직원이 결재 올리기 전에 스스로 돌리는 체크리스트라서, 모델이 이미 본 자료만 근거로 쓴다. ⑦은 상사가 정답지를 놓고 하는 평가다. ⑥이 정답을 알면 실력이 아니라 커닝을 재게 되므로 코드 구조로 막는다.

2. 어떤 업무로 잡았나

업무 하나가 아니라 직군별 업무 묶음 세 개로 잡는다. 셋은 구조가 서로 달라서, "개발에 안 쓴 업무에서도 되는가"를 시험하는 데 그대로 쓰인다(3절 범용성 수준 2).

묶음대표 과제 예도구자동 채점성격
ERP·사무 데이터거래·재고 표에서 조건 조회와 집계, 승인 규칙 적용, 이상 건 찾기표 조회(페이지 단위), 필터, 합계, 제출정답 ID 집합과 합계짧고 정확성 중심. 첫 어댑터
문서 작업규정·회의록에서 근거 찾아 답하기, 양식 채우기, 여러 문서 비교문서 목록·검색·읽기(페이지 단위), 제출정답 조항 ID, 필드 값, 인용 일치길고 방해 문서가 많다. 문맥 관리 시험장
개발로그에서 오류 원인 찾기, 설정 파일 점검, 코드 읽고 질문에 답하기파일 목록·읽기·검색(읽기 전용)정답 파일·줄·원인코드 실행은 보안 검토 뒤로
  • 순서: ERP(v1과 함께) → 문서(3단계) → 개발(4단계).
  • 규모: 묶음마다 20~50과제. 개발용과 평가용을 나누고, 되묻기·거절이 정답인 과제도 섞는다.
  • 자료: 실제 데이터는 반출할 수 없으니 구조만 받는다(표 열 이름, 문서 형식, 규칙 종류). 사외에서 합성 자료 생성기를 만들고, 사내에서는 생성기를 실행해 같은 자료를 만든다.
팀이 준비할 것: 직군별 실제 업무 예시를 5~10개씩 모아 주세요. 민감 정보는 지운 형태로, 각 예시에 ① 어떤 지시를 받는지, ② 어떤 자료를 보는지(구조만), ③ 무엇이 정답인지가 있으면 됩니다. 이것이 없으면 과제를 추측으로 만들게 됩니다.

효과는 켬/끔 비교로만 확인한다

probe는 측정이라 비교가 필요 없다. 하지만 하네스 기능이 도움이 되는지는 반드시 비교해야 안다. 같은 모델, 같은 과제, 같은 예산에서 기능만 바꿔 과제별로 짝지어 비교한다. 성공률은 과제 난이도와 모델의 무작위성으로도 흔들리므로, 한쪽만 보면 원인을 알 수 없다.

3. 왜 범용성이 있다고 하나

정확히 말하면 "범용성이 있다"가 아니라 "범용성을 시험할 수 있게 만든다"이다. 아직 GLM 실측 결과가 하나도 없다. 하네스 본체도 구현되지 않았다. 지금 주장할 수 있는 것은 두 가지뿐이다. 첫째, 구조가 범용성을 가능하게 한다. 둘째, 범용성을 검증하는 방법을 정해 두었다.

구조가 범용성을 가능하게 하는 이유

  • 업무가 바뀌어도 코어는 그대로다. 업무별 차이는 전부 어댑터 안에 있다. 그래서 새 업무를 붙일 때 이미 검증된 복구·기록·예산 기능을 그대로 쓴다.
  • 모델이 바뀌어도 코드는 그대로다. 모델별 차이는 프로필 파일에 있다. 작은 모델로 바꿀 때 프로필만 교체한다.
  • 모든 조합이 같은 기준으로 기록된다. 그래서 "이 업무에선 되고 저 업무에선 안 된다"를 공정하게 비교할 수 있다.

범용성을 검증하는 방법: 칸 채우기

세로는 업무, 가로는 모델이다. 개발할 때 쓴 칸(파랑)에서만 좋으면 범용이 아니다. 안 써본 칸(초록·주황)에서도 하네스를 손대지 않은 채 결과가 유지돼야 범용성의 증거가 된다.

4. 작은 모델의 짧은 문맥과 기억력

원칙: 기억은 모델이 아니라 하네스가 든다. 작은 모델은 공칭 문맥보다 훨씬 짧은 범위만 제대로 쓴다.

  • RULER에서 128K 모델 다수는 32K~64K까지만 기준을 넘었다.
  • GLM4-9B는 공칭 1M 중 64K(약 6%)였다.
  • 표현이 다른 질문으로 찾게 하면(NoLiMa) Llama-3.1-8B는 약 1K였다.
  • 작은 모델이 스스로 쓴 메모로는 거의 나아지지 않았다(Qwen3-4B 14.88%→16.07%). 강한 모델이 써 준 메모로는 크게 올랐다(→49.40%).

그래서 원문은 하네스가 전부 보관하고, 매 요청 때 필요한 만큼만 골라 보여준다.

그림 4. 기억은 하네스가 든다. v1에는 왼쪽 구조와 조립 함수 틀만 넣고, 가리기·상태 블록은 3단계에서 켠다.

probe.py는 어떻게 동작하나

하네스 본체를 만들기 전에 "우리 게이트웨이의 GLM이 실제로 어떻게 행동하는지"를 재는 도구다. 작은 모델의 도구 호출 실패 연구 상당수는 2B 이하 모델에서 나왔다. 반면 GLM-5.3-Flash는 총 320B·활성 18B의 큰 모델이라, 어떤 복구 기능이 필요할지 미리 알 수 없다. 그래서 먼저 잰다. 결과가 모델 프로필 0판이 된다.

그림 5. probe.py의 5단계. 총 약 40회 호출. 응답마다 입력·캐시·사고 토큰도 함께 표시한다.

구현에서 신경 쓴 점:

  • 어떤 오류에도 멈추지 않는다. 서버 거부, 연결 실패 모두 그 자리에서 기록하고 다음 시험으로 넘어간다.
  • 거부 이유 원문을 보존한다. 400이 나도 어떤 옵션이 왜 거부됐는지 알 수 있다.
  • 판정 순서에 의미가 있다. "잘림"을 먼저 확인한다. 잘린 응답은 인자도 깨져 보이므로, 인자 오류로 잘못 세지 않게 하기 위해서다.
  • 키는 화면에 안 보이게 입력받는다. 결과 파일에도 남지 않는다(가짜 서버 시험으로 확인).
  • 사고량 옵션은 자동으로 고른다. 게이트웨이가 받는 방식(최상위 필드 또는 vLLM 방식)을 1단계 결과로 판단해 2~4단계에 적용한다.
  • 한계: 서버가 옵션을 조용히 무시하는 경우는 자동으로 판정하지 못한다. 그래서 사고량 수치를 비교해 사람이 확인한다. 20회는 방향 결정용이며 통계적 증명이 아니다.

사외 개발용 Mac 모델
