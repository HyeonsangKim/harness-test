Nemotron 3 Super 자료 분석

브레인크루 리뷰와 NVIDIA 얼리 액세스 자료 2종을 읽고, 공개 원문(모델 카드·기술 보고서·vLLM 문서)으로 검증한 뒤 우리 하네스에 쓸 것을 골랐다. 2026-10-20 기준.

1. 자료2. 모델3. 브레인크루 결과4. 냉정하게 읽기5. 우리가 쓸 것6. 모델로 쓸 수 있나7. 출처
요약
  • 모델 자체는 우리 후보가 아니다. 사내 게이트웨이에 없다. Mac에서는 4비트로도 64~72GB가 든다. 한국어는 공식 지원 언어가 아니다. 공개된 도구 사용 점수(τ² 평균 61)도 이미 고른 GLM-4.7-Flash 쪽 공개값보다 낮다.
  • 브레인크루 결론("사고를 끈 fast 모드로 충분")은 절반만 맞다. 지시 따르기, 대화, 재정렬, SQL에서는 맞다. 하지만 같은 자료에서 긴 문맥 검색(RULER)은 사고를 켰을 때 0.97, 껐을 때 0.70이다. 실험은 모두 1회 실행이라 0.01~0.04 차이는 구분이 안 된다.
  • 쓸 만한 것은 모델보다 방법이다.
    • v1 설계에 넣을 것 4개: 두 가지 도구 호출 형식 복구, 사고·본문이 뒤바뀐 응답 처리, 같은 호출 반복 감지, 업무별 사고량 정책.
    • 평가 설계에 넣을 것 3개: 변별력 없는 과제 거르기, 방해 표·열을 넣은 ERP 합성 자료, 요청 문체 다양화.
    • 나중에 쓸 것 2개: LLM 재정렬, 하네스 쪽 사고 예산.
    모두 원문으로 확인했다.

3-4. 나머지

  • 검색 전처리(질문 여러 개로 바꾸기, 쪼개기, 가상 답 만들기 HyDE; 가상 시나리오 25개, LLM 채점, 5점 만점): Nemotron 4.64, GPT-5.4 4.70, GPT-4o 4.32. 차이가 작다.
  • 에이전트 사례(OpenCode + Nemotron vs Claude Code + Opus): 보고서 조사 후 PPT 만들기, 스네이크 게임. 화면 캡처 비교만 있고 점수는 없다. Nemotron 쪽 PPT는 내용이 빈약하다.
  • 후기: 쉬운 일에는 크기 대비 좋은 선택지, 추론력은 아쉬움, 요청 제한이 잦음. 부록의 세차장 문제("50m 거리 세차장, 걸어갈까 차로 갈까?")는 53개 모델 중 5개만 10회 모두 맞혔다고 인용했다. 다만 같은 사이트의 다른 실행에서는 결과가 엇갈린다.

4. 냉정하게 읽기

브레인크루 리뷰의 한계
  • 모두 1회 실행이다. 반복, 분산, 온도 설정이 없다. 표본도 작다(재정렬 50, 시나리오 25). 0.01~0.04 차이로 순위를 매긴 부분은 우연과 구분되지 않는다.
  • 결론과 자료가 어긋난다. "fast 모드로 손해 없다"고 했지만 RULER는 0.97에서 0.70으로 떨어진다.
  • MT-Bench deep 7.19는 이상치다. 사고를 켰는데 GPT-4o보다 낮다. 원인 설명이 없다. 사고 내용이 채점에 섞였거나 출력이 잘렸을 가능성이 있다(추정).
  • τ-bench 조건을 적지 않았다. 버전, 도메인, 시도 횟수가 없다. NVIDIA 공식 τ²(평균 61.15)와 직접 비교할 수 없다.
  • "Benchmark for RAG"라는 제목은 맞지 않는다. IFEval, MT-Bench, τ-bench는 RAG 벤치마크가 아니다.
  • 학습 데이터 요약은 기술 보고서와 대체로 일치한다. 20k 질의, 24개 동작 분류, GPT-OSS-120B 판정, AGENTS.md 명세, Qwen3-Coder-480B·MiniMax M2.5로 Codex·OpenCode·Qwen Code·Stirrup 기록을 수집한 부분이다. 다만 "걸러낸 것"이 무엇인지 모호하게 적었다. 보고서는 기존 코드베이스를 참조하거나 기존 파일을 고치는 과제를 제외했다고 쓴다.
NVIDIA 가이드 안의 불일치
  • 활성 파라미터를 한 곳에서 "3B"라고 적었다. 같은 문서의 다른 곳과 모델 카드는 12B, 기술 보고서는 12.7B다.
  • 권장 최대 토큰이 본문은 64K 이상, 부록은 264K다.
  • low_effort 예시에 enable_thinking이 빠졌다. 모델 카드는 둘 다 넣으라고 한다.
  • 예시 문제(서점 계산 130, 트로피 대명사 등)는 쉬워서 모델 간 변별력이 없다.

5. 우리 하네스에 쓸 수 있는 것

"모델을 바꾸자"가 아니라 "방법을 가져오자"다. 근거는 모두 원문으로 확인했다. 어디에 넣을지는 우리 구조(코어 / 어댑터 / 프로필) 기준으로 적었다.

A. v1 설계에 넣을 것

A1. 텍스트 도구 호출 복구 파서가 두 형식을 읽게 한다 확인

본문으로 샌 도구 호출은 두 가지 형식이 있다.

  • GLM 형식: <tool_call>이름<arg_key>키</arg_key><arg_value>값</arg_value>
  • Qwen3 계열 XML 형식: <tool_call><function=이름><parameter=키>값</parameter>…

Nemotron 3 Super와, 우리가 Mac 개발용으로 고른 Qwen3.5·Qwen3.6이 모두 vLLM에서 qwen3_coder 파서를 쓴다. 둘만 읽으면 사내 GLM과 사외 Mac 모델을 모두 다룰 수 있다.

넣을 곳: 코어의 프로토콜 복구 계층. 어떤 형식인지는 모델 프로필에 적는다. probe의 txtfmt가 이미 glm/json을 구분한다.

A2. 사고와 본문이 뒤바뀌거나 사고 태그가 비어 있는 응답을 처리한다 확인
  • NVIDIA 가이드: 사고를 켜도 <think></think>가 빈 채로 나올 수 있고, 이게 정상이다.
  • vLLM 파서: 사고를 끈 상태에서 본문이 비면 사고 칸과 본문 칸을 서로 바꿔 돌려준다.

그래서 "본문이 비었고 사고 칸에 답이 있음"을 실패로 보지 않고 별도 유형으로 기록해 처리한다. GLM에서도 같은 일이 생길 수 있다.

넣을 곳: 코어 응답 해석 + 실패 유형 분류표.

A3. 같은 도구를 같은 인자로 반복 호출하면 감지한다 확인

NVIDIA는 빈 폴더에서 없는 파일을 고치려는 과제를 학습 데이터에서 일부러 뺐다. 기술 보고서는 그런 상황이 "redundant and exhausted tool invocations", 즉 쓸데없는 호출을 소진될 때까지 반복하는 상황으로 자주 이어진다고 쓴다.

큰 모델도 학습으로 막아야 했던 실패라면, 작은 모델에서는 더 자주 나온다고 봐야 한다. 그래서 하네스가 같은 호출의 반복 횟수를 세고, 정해진 횟수를 넘으면 "이미 같은 결과를 받았다"는 안내를 도구 결과 안에 넣거나 중단한다.

넣을 곳: 코어 루프(예산 규칙과 같은 자리). 반복 상한은 어댑터가 정한다. 실패 카탈로그에 "반복 호출" 태그를 처음부터 둔다.

A4. 사고량은 모델 하나에 하나가 아니라 업무별로 정한다 브레인크루 1회 실측 + 모델 카드

지시 따르기, 대화, 재정렬, SQL에서는 사고를 줄여도 같거나 더 나았고 15배 빨랐다. 긴 문맥 찾기에서만 사고가 크게 도왔다(0.97 대 0.70).

GLM-5.3-Flash는 사고를 끌 수 없지만 low/high/max는 고를 수 있다. 그래서 모델 프로필의 사고량 값을 하나로 두지 않고, 어댑터가 업무별 기본값을 요청하고 seed 구간 실측으로 고정한다. 기존 계획("effort를 seed 구간에서 골라 고정")을 업무 단위로 세분하는 것이다.

넣을 곳: 프로필의 정책 값 + 어댑터 설정.

B. 평가 설계에 넣을 것

B1. 변별력 없는 과제를 미리 거른다 확인

NVIDIA는 도구 사용 학습 데이터를 고를 때 16번 실행해서 전부 성공하거나 전부 실패한 시나리오를 버렸다. 우리 비교(기본 대 복구 켬 등)에서도 이런 과제는 정보가 없다.

다만 같은 실행 결과로 거르면 결과가 유리하게 치우친다. 그래서 seed 구간 예비 실행으로만 거르고, 비교 실험 구간과 섞지 않는다.

브레인크루 NL2SQL처럼 12B 모델과 GPT-5.4가 같은 점수를 받는 과제는 하네스 차이도 보여주지 못한다. 과제 세트를 확정하기 전에 "약한 설정과 강한 설정의 점수가 실제로 갈리는지"를 확인한다.

B2. ERP 합성 자료에 방해 표·열과 다양한 요청 문체를 넣는다 확인

NVIDIA의 SQL 학습 데이터(9.65만 건)는 두 가지 장치를 썼다.

  • 방해 요소: 관련은 있지만 쓸모없는 표와 열을 일부러 섞어 실제 업무 DB처럼 지저분하게 만들었다.
  • 요청 문체 3축: 지시 방식(명령, 서술, 질문, 맥락 설명, 축약), 말투(격식, 대화체, 전문, 학술, 직설), 공손도.

우리 ERP 합성 자료 생성기에 그대로 옮길 수 있다. 예를 들어 "3분기 부서별 미결 전표 합계"를 "3분기 미결 전표 부서별로 좀 뽑아줘", "팀장님이 3분기 미결 건 부서별로 보고 싶어하시는데요"처럼 바꾸고, 비슷한 이름의 표(전표, 전표_백업, 전표_임시)를 섞는다. 브레인크루 결과로 보면 한국어 질문은 영어보다 1~4포인트 낮으므로, 한국어 문체 다양성이 실제 난이도를 만든다.

넣을 곳: 0'단계 업무 예시 수집 이후의 합성 자료 생성기(ERP 어댑터).

B3. 업무 과제 생성 순서를 NVIDIA의 6단계에서 빌린다 확인
1. 영역세부 영역으로 넓히기
2. 규칙·도구정책과 도구를 만들고 다듬기
3. 상황요청자, 배경, 요청
4. 실행상황마다 16번
5. 검증결과와 과정을 LLM이 판정
6. 선택전부 성공·전부 실패 제외
1. ERP 영역구매, 회계, 재고…
2. 업무 규칙·도구사내 예시의 구조로
3. 요청 상황B2의 문체 3축
4. 실행3회 반복
5. 검증정해진 채점 코드 (LLM 채점 안 씀)
6. 선택seed 구간에서 B1 거르기

위: NVIDIA 대화형 도구 사용 데이터 생성 순서. 아래: 우리 ERP 평가 과제에 옮긴 모습. 차이는 5단계다. 우리는 판정을 LLM에 맡기지 않고 정답 비교 코드로 한다. 브레인크루처럼 LLM 채점에 기대면 작은 차이를 믿을 수 없기 때문이다.

C. 나중에 쓸 것

C1. LLM 재정렬 (3단계 문서 업무 어댑터) 브레인크루 1회 실측

한국어 문서에서 BM25 다음에 LLM이 20개씩 다시 줄 세우면 NDCG@10이 0.32에서 0.53으로 올랐다. 사고를 줄인 모드로 충분했다. 브레인크루는 형태소 분석기 Kiwi를 썼지만, 우리는 표준 라이브러리만 쓰므로 2글자 단위 색인으로 1차 후보를 뽑는다. 이 조합의 효과는 우리가 다시 재야 한다.

C2. 하네스 쪽 사고 예산 (GLM 사고가 너무 길 때의 대안) 방법은 확인, 우리 환경 적용은 미확인

Nemotron의 예산 기능은 모델이 아니라 호출하는 쪽에서 구현한다.

  1. 사고를 예산 토큰만큼만 받는다.
  2. 받은 사고 끝에 닫는 태그를 붙여 assistant 메시지로 넣고, 이어서 쓰게 해 답을 받는다.

두 가지가 걸린다.

  • 사내 게이트웨이가 "이어 쓰기"(continue_final_message)를 허용해야 한다. 담당자에게 물을 수 없으니 probe로 확인해야 한다.
  • Nemotron은 잘린 사고로 학습했지만(학습 데이터의 12%), GLM은 그렇지 않아 품질이 떨어질 수 있다.

effort=low로도 사고가 너무 길 때만 시험한다.

D. 쓰지 않을 것

  • 검색 전처리(질문 바꾸기·쪼개기·HyDE): 모델 간 차이가 작고(4.32~4.70) 채점도 LLM이 했다. 문서 업무에서도 후순위로 둔다.
  • 단발 상식 퀴즈(세차장 문제 등)로 모델 고르기: 표현과 실행마다 결과가 갈린다. 우리는 업무 과제로 반복 측정한다.
  • 브레인크루 모드 비교를 GLM에 그대로 적용하기: 다른 모델이고 1회 실행이다. 방향 참고로만 쓴다.

6. Nemotron 3 Super를 우리 모델로 쓸 수 있나

용도판단이유
사내 본 모델해당 없음사내 게이트웨이에 없다. 나중에 들어오면 probe를 그대로 돌리면 된다. 도구 형식(Qwen3 XML)은 A1로 이미 대비된다
Mac 개발·대역 모델권장 안 함4비트 64~72GB라 64GB Mac도 빠듯하다. 한국어 공식 미지원. τ² 평균 61.15로 GLM-4.7-Flash 공개값(79.5)보다 낮다(측정 조건이 달라 참고용). 같은 도구 형식은 더 작은 Qwen3.5-9B / Qwen3.6-35B-A3B로 시험할 수 있다
긴 문서 업무 비교군보류RULER@1M 91.75로 긴 문맥은 강하다. 사내에 들어오면 3단계 문서 업무에서 비교할 가치가 있다
