# selection_draft.md 논리·설계 검토 (수치 검증 제외)

검토 범위: 단계 배치, 설계 정합성, 평가 설계, 구현 가능성(표준 라이브러리·Windows·손타이핑), 누락, 과장. 수치 자체는 별도 검토자가 본다.
참고: DESIGN_KO.md, REPORT_KO.md(프로필 스키마·모듈 표·보안 기본값·단계표), probe.py, 같은 폴더 노트 3개.
표기: [확인]은 이 저장소 문서에서 직접 확인한 것, [추론]은 검토자 판단, [확인 필요]는 사내/모델 파일에서 확인해야 할 것.

## 요약

초안의 방향(하네스가 기억을 든다, 결정적·복구 가능한 기법 우선, LLM 요약은 최후)은 노트·설계와 맞다. 문제는 세 가지다.

1. **v1(A)에 기능은 너무 많고, 나중에 고치기 비싼 "데이터 구조 결정"은 빠져 있다.** 상태 블록 렌더러, grep_obs, 문자 종류별 보정은 미뤄도 된다. 반대로 "이력 원본은 불변, 문맥은 매번 렌더링", "관찰 ID 고정", "모델이 본 범위 기록", "재진입 가능한 루프"는 v1에서 정해야 한다.
2. **GLM의 사고 내용(reasoning_content)이 문맥에 쌓이는 문제를 다루지 않는다.** 그런데 상태 블록 위치(마지막 user 메시지)가 GLM 채팅 템플릿의 사고 유지 규칙과 부딪칠 수 있다. 그러면 A5를 켜고 끈 비교가 사고 가시성 차이로 오염된다.
3. **B·C·D 항목마다 "효과를 어떻게 보일지"가 없다.** 특히 GLM(약 1M 창)에서 3단계 과제를 돌리면 마스킹이 아예 발동하지 않을 가능성이 크다. 그러면 v0의 S처럼 "측정 불가"가 반복된다.

## High

### H1. 상태 블록을 "마지막 메시지"에 붙이는 방식: 메시지 순서 제약 + GLM 사고 유지 규칙과 충돌
- **위치:** A5 "시스템 프롬프트가 아니라 마지막 메시지에 붙임", A1의 "[끝: 상태 블록]".
- **문제:**
  1. **OpenAI 형식 제약 [확인 필요: 게이트웨이].** `tool_calls`가 있는 assistant 메시지 바로 뒤에는 각 `tool_call_id`에 대한 tool 메시지가 모두 와야 한다. 그 사이에 user 메시지를 끼우면 OpenAI 호환 서버가 400을 내거나 템플릿이 깨진다. tool 메시지들 **뒤에** 오는 user 메시지는 형식상 허용된다. 초안은 "마지막 메시지"가 별도 user 메시지인지, 마지막 tool 메시지 본문인지 정하지 않았다.
  2. **사고 유지 규칙 [확인 필요: chat_template.jinja].** GLM-4.5 계열 이후 템플릿은 대체로 "마지막 user 메시지 이후의 assistant 턴만 reasoning_content를 렌더링"한다. `clear_thinking=false`일 때만 전부 유지한다. REPORT_KO.md도 이 템플릿을 인용한다. 상태 블록을 매 턴 새 user 메시지로 끝에 붙인다고 하자. 그러면 이전 assistant 턴이 전부 "마지막 user 이전"이 되어 사고가 지워진다. 결과는 두 가지다. (a) 렌더링된 앞부분이 매 턴 바뀌어 prefix cache가 거의 0이 된다. (b) 모델이 자기 이전 사고를 못 본다. **A5 on/off 비교의 차이가 상태 블록 효과인지, 사고 가시성 효과인지 구분되지 않는다.**
  3. 같은 문제는 다른 곳에도 있다. 프로토콜층의 "도구를 쓰거나 제출하라" 재촉, 실행 중 검사 피드백도 user 메시지로 넣으면 같은 일이 생긴다.
- **수정 문구(A5 교체):**
  > 상태 블록은 **마지막 tool 메시지의 content 끝**에 `<state>…</state>`로 덧붙인다. 원본 이력에는 저장하지 않고, 렌더링할 때만 붙인다. 다음 턴에는 이전 위치에서 지워지고 새 마지막 tool 메시지에 붙는다. 그래서 캐시 손실은 꼬리 한 메시지로 끝난다. 첫 턴(아직 tool 메시지가 없을 때)에는 과제 user 메시지 끝에 붙인다. 병렬 호출이면 마지막 tool 메시지에 붙인다. **과제 진행 중 하네스가 만드는 글(검사 결과, 경고)은 가능하면 tool 메시지로 넣는다.** 도구 미호출 재촉처럼 user 메시지가 불가피한 경우에는 기록에 `harness_user_turn` 사건으로 남긴다.
- **추가 확인(0단계, 몇 줄):** probe에 "tool 결과 뒤 user 메시지"를 넣은 왕복을 추가한다. HTTP 상태와, 이전 턴 사고가 `prompt_tokens`에 반영되는지(같은 대화를 user 메시지 유무로 보내 `prompt_tokens` 차이 확인)를 본다.

### H2. 사고 내용 누적을 다루지 않고, "오래된 사고 블록 삭제"를 기각한 근거가 조건부다
- **위치:** E 마지막 항목. A1~B1 전체(도구 결과만 관리 대상).
- **문제:**
  - GLM-5.3-Flash는 사고가 항상 켜져 있고 effort 기본값이 max다 [확인: REPORT 근거 1·로드맵]. 한 과제 안에서는 user 메시지가 처음 하나뿐이다. 그래서 템플릿 규칙상 이전 턴의 사고가 **전부 유지**된다(H1의 규칙). 긴 업무에서는 사고 토큰이 도구 출력보다 문맥을 더 빨리 채울 수 있다. 그러면 B1(도구 결과 마스킹)만으로는 하한(40%)에 못 내려가 M1의 "헛발동"이 생긴다.
  - 기각 근거인 "Preserved Thinking 시 원문 반환 요구"는 `clear_thinking=false`일 때만 적용된다. REPORT는 이것이 Z.ai 표준 API 기본값이 아니라고 적었다 [확인: REPORT 59행]. 또 probe.py `roundtrip()`이 이미 `keep_reasoning`/`drop_reasoning` 두 경우를 시험한다 [확인]. 즉 "지워도 되는지"는 0단계 결과로 바로 판정된다.
- **수정 문구(E에서 빼고 B4로 신설):**
  > B4. 사고 이력 보존 정책(프로필 플래그 `reasoning_history: all | last_k | none`). 기본값 all. 다른 값은 두 조건을 모두 만족할 때만 허용한다. ① probe의 `rt_2_drop_reasoning`이 정상(200, 결과 사용) ② 프로필 `clear_thinking`이 false가 아님. v1에서는 구현하지 않고 **턴별 토큰 구성(사고 토큰 / 도구 결과 추정 토큰 / 기타)만 기록**한다. 3단계에서 사고 누적이 문맥의 큰 몫을 차지하면 B1과 같은 과제로 all 대 last_k를 비교한다. 위험: 궤적 증폭(2609.29875 저자 경고). 근거: 초록만 확인(V, 약함).
- v1 비용: 기록 1~3줄(`usage.completion_tokens_details.reasoning_tokens`, 이미 probe가 읽는 필드).

### H3. v1에서 정해야 할 것은 "기능"이 아니라 "고치기 비싼 데이터 구조"다
- **위치:** A 전체. 비용 추정.
- **문제:** B1·B2·C3·D를 나중에 붙일 때 코어를 다시 뜯게 만드는 결정이 A에 명시돼 있지 않다. 손타이핑 환경에서는 v1 이후 코어 수정이 가장 비싸다(DESIGN ⑤: "한 번만 타이핑").
- **수정 문구(A0로 맨 앞에 추가):**
  > A0. v1에서 고정하는 구조(코드 양은 적고, 나중에 바꾸기 비싼 것):
  > 1. **원본 이력은 불변(append-only) 사건 목록**으로 둔다. 모델에게 보내는 메시지는 `render(history, state, profile)`이 매번 새로 만든다. 마스킹·상태 블록·사고 정책은 모두 render 안의 변환이다. 이력 리스트를 제자리에서 고치지 않는다.
  > 2. **관찰 ID**: 도구 결과마다 `obs_<step>` ID를 붙인다. 원문은 trace에 이미 남으므로 **trace가 곧 관찰 저장소**다. 별도 저장소를 두지 않는다. 재개(resume) 시에도 ID가 유지된다.
  > 3. **"모델이 본 것" 기록 단위는 (obs_id, 시작, 길이)** 범위로 한다. 잘림·마스킹이 생기면 "읽은 문서"와 "본 부분"이 달라진다. 실행 중 검사의 "인용한 자료를 실제로 봤는가"가 이 범위를 기준으로 판단해야 한다. 마스킹으로 지금 보이지 않는 것도 "본 적 있음"으로 친다.
  > 4. **trace에 렌더링된 요청을 남긴다**(또는 재현 가능한 render 입력 + render 버전). 마스킹 효과를 분석하려면 "모델이 실제로 본 문맥"이 필요하다.
  > 5. **루프는 재진입 가능**하게 둔다: `run(task_spec, tools, profile, budget, trace, parent_id=None)`, 전역 상태 없음. trace 사건에 `run_id`/`parent_id`를 넣는다. 그러면 B2(맵 워커)를 루프 수정 없이 붙일 수 있고, 예산도 하위 실행까지 합산할 수 있다.
  > 6. **직렬화 결정성**: JSON은 `sort_keys=True`, 같은 `ensure_ascii` 설정으로 직렬화하고, 접두부에는 타임스탬프를 넣지 않는다.

### H4. A가 v1에 넣기에는 크고, 프로젝트 원칙("측정 먼저, 기능은 나중")과 어긋난다. 줄 수 추정도 낮다
- **위치:** A3, A5, A2의 grep_obs, 비용 추정 "70~100줄".
- **문제:**
  - **A5:** "구현은 v1, 기본 꺼짐"은 2단계에서 한 번도 실행되지 않는 코드를 손으로 쳐 넣는다는 뜻이다. 테스트되지 않은 경로가 생기고, 설계(고정 사실 출처, 위치 H1)는 아직 없는 3단계 과제에 좌우된다. DESIGN ②와 REPORT 3단계("메모는 정보 손실이 관찰될 때만")와 모순된다. 나중에 붙이는 비용은 H3-1의 render 함수 안 약 10~20줄이라 크지 않다.
  - **A3:** 문자 종류별 비율 + 이동평균 + 프로필 저장은 GLM 1M 창에서는 쓸 곳이 거의 없다. 정밀 추정이 필요한 곳은 5단계(작은 창)다.
  - **줄 수(추론):** render 15~20, 래퍼+핸들+도구 정의 2개(스키마 dict만 각 8~10줄)+핸들 검증 40~50, 추정·보정·저장 20~25, 상태 블록 렌더+고정 사실+모델 수정 필드(=도구 하나 더) 30~40, 프로필 필드 5~10. 합하면 **약 110~150줄에 테스트는 별도**다. REPORT의 본체 목표(530~750줄)의 15~20%를 차지한다.
- **수정 문구(A 재구성):**
  > v1 = A0 + A1(render에 꼬리 자리만 둠, 기본 None) + A2(잘라내기 + 핸들 + `read_obs` 하나, H5·M2 반영) + A3 최소판(M4: 직전 `prompt_tokens` + 새 메시지 추정) + A4(필드만 정의, 기본값 규칙 포함). 약 45~70줄 + 재생 테스트.
  > A5 상태 블록 렌더러, 고정 사실, 문자 종류별 보정은 3단계로 옮긴다(B0). v1에는 "꼬리 자리"와 상태층의 사실 기록(이미 state.py 역할)만 둔다.
  > 비용 추정 문구: "v1 추가분 약 45~70줄(추론). 초안 A 전체를 넣으면 약 110~150줄 + 테스트."

### H5. 머리+꼬리 잘라내기는 첫 어댑터(엑셀형 집계)에서 조용히 오답을 만든다. 2단계 기준선(B)도 바꾼다
- **위치:** A2.
- **문제:**
  - 표·목록 결과에서 가운데 행을 빼면, 모델이 남은 행만으로 합계를 낸다. 오답이 **절차 실패가 아닌 wrong_answer로 보인다.** "생략 표시"만으로는 작은 모델이 read_obs를 부를지 보장할 수 없다(근거 없음).
  - 2단계는 "B(복구 on/off)·V·R"를 비교하는 단계다 [확인: REPORT 로드맵]. 잘라내기가 발동하면 B의 정의가 바뀐다. v0 대비 재생 테스트("도구 실행 순서·상태·채점 결과가 같음")도 깨질 수 있다.
- **수정 문구(A2에 추가):**
  > 잘라내기 방식은 **도구별로 어댑터가 선언**한다: `head_tail`(로그·오류), `head`(목록·파일), `refuse`("결과가 N자를 넘음, offset/limit 인자로 나눠 요청하라"는 오류를 반환. 표·집계용 권장). 기본값은 `head_tail`. 잘릴 때마다 `truncated` 사건(obs_id, 원래 길이, 남긴 길이)을 기록한다. 실패 태그에 `truncated_needed`(필요한 내용이 잘린 부분에 있었음)를 추가한다. 2단계 GLM 프로필에서는 `max_tool_output`을 v0 과제의 최대 출력보다 크게 둔다. 그러면 잘라내기가 사실상 꺼지고, 발동 0회를 기록으로 확인할 수 있다.
- **근거 표기 수정:** LongFuncEval은 "출력이 길면 나빠진다"의 근거다. "머리+꼬리가 그것을 막는다"의 근거가 아니다. 초안의 "(추론)"을 문장 앞으로 옮겨 A2 전체가 추론임을 분명히 한다.

### H6. B·C·D 평가 설계가 없다. 특히 B1은 GLM에서 발동조차 안 할 수 있다
- **위치:** B 머리말 "켜고 효과를 잰다", B1~D4.
- **문제:**
  - GLM은 약 1M 창이다. 3단계 과제(20~50개, 20턴 이상)에서는 `context_tokens_safe`의 70%에 거의 닿지 않는다. 그러면 마스킹 on/off는 같은 결과가 나오고 "효과 없음"이 된다. 이것은 DESIGN이 v0 S에 대해 지적한 실패와 같은 구조다.
  - JetBrains 결과처럼 효과의 부호가 모델마다 뒤집힌다 [확인: 노트]. 그래서 "켜면 좋다"는 가정 없이 비열등성(non-inferiority)으로 판정해야 한다.
- **수정 문구(B 머리말에 "평가 규칙" 추가):**
  > 평가 규칙(B·C·D 공통):
  > - **같은 과제·같은 seed의 짝지은 비교**를 한다. 결과 행은 REPORT 고정 형식을 따른다(정답 일치와 형식 충족 분리, 토큰, 지연, 호출 수, 복구 발동 수, 실패 태그).
  > - 각 행에 **기법 발동 횟수**(마스킹 횟수, 잘림 횟수, read_obs 호출 수, 상태 블록 토큰)를 넣는다. 발동 0이면 그 행은 효과 판정에서 뺀다.
  > - 판정 기준을 미리 적는다. 예: "입력 토큰 −30% 이상이면서 성공률 하락 5%p 이내면 채택(비열등)", "성공률 +10%p 이상이면 채택(우월)". n=20~50의 성공/실패 짝 비교로는 대략 15~20%p보다 작은 차이를 구분하기 어렵다(추론). 그러니 작은 차이는 "판정 보류"로 적는다.
  > - **창을 일부러 줄이는 시험(budget clamp):** 3단계에서 GLM 프로필의 `context_tokens_safe`를 16K/32K로 강제한 조건을 추가한다. 그러면 작은 모델 없이도 B1의 동작(발동, 복구, read_obs 사용)과 비용 효과를 먼저 검증할 수 있다. 5단계에서는 "기법이 작동하는가"와 "작은 모델이 그것을 쓰는가"만 따로 보면 된다.
- **항목별 대조군(추가 표):**

  | 항목 | 비교 조건 | 대조군(비용·길이 맞춤) | 핵심 지표 |

  | B0(구 A5) 상태 블록 | off / on | **같은 토큰 수의 가짜 블록**(과제 원문만 다시 적기). "다시 적기 효과"와 "구조화 사실 효과"를 분리 | 성공률, 목표 이탈·조건 누락 태그 |

### H7. C1 판정 규칙이 통계적으로 약하고, 배치(5단계)가 A4·B1의 필요 시점보다 늦다
- **위치:** C1, A4.
- **문제:**
  1. 칸당 5회에 "1K 대비 85%"를 적용하면, 기준 정확도가 1.0일 때 0.85 이상은 사실상 5/5다. 노트 원안대로 "모든 깊이에서"를 요구하면 더 엄해진다. 참 정확도가 0.9인 길이도 칸 하나가 5/5에 실패할 확률이 약 41%다. 깊이 세 칸이면 대부분 탈락한다. 그래서 effective_ctx가 아래로 치우치고 실행마다 흔들린다(추론, 이항 계산).
  2. "각 칸 5회, 온도 0"이면 같은 입력에서 거의 같은 출력이 나온다. 5회가 의미 있으려면 바늘 내용·위치·seed를 바꿔야 한다. 노트에는 이 조건이 있는데 초안에서는 빠졌다. 또 사고 모델은 greedy 디코딩에서 반복 루프가 생긴다는 보고가 있다(Qwen3 계열 권고, [확인 필요]). 측정은 **프로필의 운영 온도**로 해야 실제 사용 조건과 맞는다.
  3. A4는 "고정 비율 대신 실측값"이라고 하면서, 실측(C1)은 5단계다. 그러면 2~3단계 GLM의 `context_tokens_safe`를 정할 규칙이 없다.
  4. 측정 상한이 64K면 GLM의 effective_ctx는 구조상 64K 이하로 나온다. 이것은 "측정 상한에서 잘린 값"이다.
- **수정 문구:**
  > C1 판정: 길이마다 깊이를 합쳐 15회(과제별)로 정확도를 낸다. `acc ≥ max(0.85×base, 0.80)`을 만족하는 최대 길이를 쓰되, **연속 두 길이에서 실패해야 중단**한다. 시행마다 바늘 내용·위치·seed를 바꾸고, 온도는 프로필 운영값을 쓴다. 측정 상한에서도 통과하면 `effective_ctx = ">=상한"`으로 기록하고 상한 값을 쓴다.
  > A4 기본값 규칙: `effective_ctx`가 null이면 `context_tokens_safe = min(context_tokens, 프로필에 적은 보수적 상수)`로 두고 `safe_source: "default"`를 기록한다. GLM은 3단계 전에 T1·T4만 줄여 돌린 C1-lite(약 60~90회)로 값을 채운다.

### M1. 70%→40% 발동 규칙: 출력 예약, 헛발동, 한 번에 넘치는 경우가 빠짐
- **위치:** B1 "발동: 70% 초과 시 40%까지", A4.
- **문제와 수정:**
  - **출력 예약:** 사고 모델은 출력 토큰(사고 포함)이 같은 창을 쓴다. `context_tokens_safe`는 **입력 상한**으로 정의해야 한다: `context_tokens − max_output − 여유`. 이 정의를 A4에 적는다.
  - **헛발동:** 사고 누적(H2), 고정 접두부, 최근 N개 보존 때문에 40%에 못 내려가면, 매 턴 70%를 넘어 매 턴 마스킹한다. 그러면 캐시가 매 턴 깨진다. 수정: "오래된 것부터 마스킹하되 최근 N개는 남긴다. 더 마스킹할 것이 없으면 `mask_exhausted`를 기록한다. 다음 발동은 입력이 그 뒤로 `clear_at_least`(예: safe의 10%)만큼 늘었을 때만 한다."
  - **한 번에 넘침:** 작은 창(8K)에서는 결과 하나가 70%에서 100% 넘게 밀어 올릴 수 있다. 보내기 전 검사를 넣는다: "추정치가 safe를 넘으면 수위와 무관하게 즉시 마스킹한다. 새 결과의 cap은 `min(max_tool_output, 남은 예산)`으로 한다."
  - **설정 불변식(로드 시 검사, 1~2줄):** `접두부 토큰 + keep_last × max_tool_output ≤ 0.4 × safe`. 이것이 성립하지 않으면 하한 40%는 도달 불가능하다.
  - **표기:** 70/40은 노트 작성자의 추론이다. 초안 B1은 이 숫자를 JetBrains·Anthropic 근거 옆에 두어 근거가 있는 값처럼 읽힌다. "(추론, 노트 Q1·Q7)"로 표시한다.

### M2. read_obs/grep_obs와 max_exposed_tools의 충돌. 도구 목록은 과제 중 고정해야 한다
- **위치:** A2, A4, C2.
- **문제:** REPORT는 v1에 `ask_user`/`final_answer`/`decline`을 도구로 넣는다 [확인]. 여기에 read_obs·grep_obs를 더하면 **코어 도구만 5개**다. 작은 모델의 `max_exposed_tools`가 5~10이면 업무 도구 자리가 거의 없다. 또 "잘림이 생기면 그때 read_obs를 노출"하는 방식은 도구 정의(고정 접두부)를 과제 중에 바꾼다. 그러면 캐시가 깨지고, 모델이 갑자기 새 도구를 보게 된다(Manus 권고 위배).
- **수정 문구:**
  > 코어 도구는 `read_obs(id, offset=0, length=?, find="")` **하나**로 합친다. `find`는 부분 문자열 검색이다(M6). 노출 여부는 과제 시작 시 어댑터·프로필이 정하고, 과제 중에는 바꾸지 않는다. `max_exposed_tools`는 **실행 전 검사**로만 쓴다: 코어 도구 + 어댑터 도구 수가 상한을 넘으면 시작을 거부하고 이유를 기록한다. 실행 중에 도구를 고르는 기능은 넣지 않는다. 상한을 넘는 업무는 어댑터가 단계별 도구 묶음이나 B2 분해로 다시 설계한다.

### M3. 고정 사실(pinned)의 출처와 자격정보 처리
- **위치:** A5 "어댑터가 지정한 고정 사실", B1 "ID·자격정보 등은 상태 블록으로 옮겨 보존".
- **문제:**
  - "어댑터가 지정"이 무엇을 뜻하는지 불명확하다. 코어 정규식으로 추출하면 업무 지식이 코어로 들어오고(경계 규칙 위반, DESIGN 4절), 오탐도 많다.
  - 자격정보를 상태 블록에 넣으면 매 호출 문맥에 다시 실리고, trace에도 남는다. 이것은 DESIGN의 "키·인증 정보는 기록하지 않는다"와 충돌한다.
- **수정 문구:**
  > 고정 사실은 **어댑터 도구가 결과와 함께 돌려준다**: `(text, facts: dict)`. 코어는 facts를 출처 단계와 함께 상태에 저장만 한다. 코어에는 업무별 정규식을 두지 않는다. 어댑터는 `never_mask` 도구 목록(Anthropic `exclude_tools`에 해당)도 선언할 수 있다.
  > **자격정보·토큰은 모델 문맥에 넣지 않는다.** 하네스가 보관하고, 도구 실행 시 하네스가 주입한다. 모델에게는 `session=<id>` 같은 참조만 보인다. 이렇게 하면 AppWorld 소형 모델의 최다 실패 범주(인증 정보 손실)를 마스킹과 무관하게 막을 수 있다(추론).

### M4. 토큰 추정: 전체 비율 보정보다 "직전 실측 + 증분 추정"이 정확하고 짧다
- **위치:** A3.
- **문제:**
  - 전체 프롬프트에 하나의 비율을 이동평균하면 한국어·영어·JSON 비중이 바뀔 때 오차가 크다.
  - 서버가 렌더링한 프롬프트는 보낸 메시지와 다르다(도구 정의 렌더링, 사고 유지 규칙 H1·H2, 템플릿 토큰).
  - 1.3~1.5자/토큰은 Qwen3-8B 단일 단락 값이다. GLM 토크나이저 값은 아니다.
- **수정 문구:**
  > `estimate(next) = 직전 usage.prompt_tokens + 직전 completion_tokens(사고 포함, 사고가 이력에 남는 프로필일 때) + est(새 메시지) × 1.15`. `est`는 보수적으로 둔다: 한글 음절 1.0토큰/자, 그 외 0.3토큰/자. 첫 호출에만 전체 추정을 쓴다. 문자 종류별 보정은 5단계로 미룬다.
  > probe에는 보정 호출 3개를 추가한다(한국어·영어·JSON 각 약 4K자, `max_tokens=1`, 빈 프롬프트 기준값을 빼기). 도구 정의 토큰도 도구 유무 차이로 한 번 잰다. 0단계에서 GLM의 실제 비율을 얻는 비용은 약 10줄이다.

### M5. sqlite FTS5 trigram: 가용성 위험 + 한국어 2음절 단어 문제
- **위치:** D3.
- **문제:**

### M6. 관찰 저장소·read_obs의 보안
- **위치:** A2.
- **문제와 수정:**
  - **핸들 = 경로 금지.** 노트의 자리표시 예시는 `.runs/<id>/obs_007.txt`처럼 경로를 보여준다. 그러면 모델이 파일 도구로 그 경로를 열려 하거나, 경로 탈출 인자를 시도할 수 있다. 수정: 핸들은 `^obs_\d+$`만 받는 불투명 ID로 하고, 하네스 내부 dict/trace 색인으로만 푼다.
  - **정규식 금지.** `grep_obs(pattern)`에 모델이 만든 정규식을 그대로 넣으면 큰 텍스트에서 파국적 역추적이 생길 수 있다. Python `re`에는 타임아웃이 없어 하네스가 멈춘다. 잘못된 패턴은 `re.error`를 낸다. 수정: 부분 문자열 검색(`in`, `str.find`) + 일치 수 상한 + 줄 단위 결과.
  - **재노출도 자료로 감싼다.** read_obs 결과도 원래 도구 결과와 같은 "자료" 래퍼로 감싼다(REPORT 보안 기본값 "문서 주입 대비"). 마스킹 자리표시에는 도구 인자를 넣는데, 인자가 문서에서 온 문자열일 수 있으므로 길이를 제한한다.
  - **보존 규칙.** 저장소를 trace와 별도로 두면 사내 문서 원문의 두 번째 사본이 생긴다. H3-2처럼 trace를 저장소로 쓰고 trace 보존 규칙 하나만 적용한다.

- **누락과 수정:**
  - **이력 없는 교정자(history-free corrector).** AppWorld Qwen3-8B 절제에서 측정 효과가 가장 컸다(노트 Q6. 수치는 사실 검증자 몫). 구현도 싸다. 이 노트 범위 밖이라면 E에 "검증·복구 노트로 넘김"이라고 한 줄 적는다. 범위 안이라면 C(5단계)에 넣는다.
  - **GLM을 교사로 쓰는 경로.** D1은 "강한 모델·사람"이라고만 적었다. 폐쇄망에서 현실적인 교사는 GLM-5.3-Flash다. 수정: "D1의 기본 교사는 GLM-5.3-Flash. 2~3단계에서 검사를 통과한 GLM trace(이미 원문 보존)를 재료로 플레이북을 쓴다. AMD의 교사는 GPT-5-mini였으므로 GLM 교사의 효과는 추론이다. GLM 도구 사용 습관이 작은 모델에 맞지 않을 수 있으므로 H6의 위약 대조로 확인한다."
  - **D2 함수 메모의 재료와 시점.** 실패 사례 카탈로그(REPORT 자산 ③)가 "도구 X의 알려진 함정"의 자연스러운 출처다. D2는 정확 키 조회라 D3의 저장소(sqlite)에 의존하지 않는다. 약 10~15줄이다. 수정: "D2는 D3와 분리한다. 5단계(작은 모델)에서 도구 오류 회복률이 낮을 때 먼저 시험한다."
  - **never-mask 목록**(Anthropic `exclude_tools`)은 노트에 있지만 초안에 없다. M3에서 반영.

### M8. prefix cache 이점이 사내 게이트웨이에서 확인되지 않았다
- **위치:** A1 근거, B1 발동 설계 전반.
- **문제:** 캐시 논거는 정확도가 아니라 지연·비용의 문제다(REPORT도 "부차적"으로 낮췄다 [확인]). 그런데 사내 게이트웨이가 prefix caching을 하는지, `usage.prompt_tokens_details.cached_tokens`를 돌려주는지 모른다. 노트 Q5도 "캐시가 없으면 캐시 고려는 덜 중요"라고 적었다.
- **수정 문구:** A1에 "캐시 이점은 게이트웨이가 prefix caching을 할 때만 해당한다. probe에서 같은 요청을 두 번 보내 `cached_tokens`와 지연을 비교한다(약 3줄)." 단, append-only 구조 자체는 재현성과 재생 테스트 때문에 캐시와 무관하게 유지한다.

### M9. B2 맵 워커: 코어 영향과 비용 대조
- **위치:** B2.
- **문제:** 하위 실행의 trace·예산·동시성 합산이 필요하다. 루프가 재진입 불가이면 코어를 수정해야 한다(H3-5). 또 "+90.2%"는 토큰을 약 15배 쓴 결과다. 같은 토큰을 쓴 단일 문맥과 비교하지 않으면 "더 많이 써서 좋아졌다"를 구분할 수 없다(H6 표).
- **수정 문구:** B2 근거 뒤에 "효과 판정은 같은 총 토큰 예산의 단일 문맥 대조로 한다. 루프 재진입성은 v1(A0-5)에서 확보한다."를 추가한다.

## Low

### L1. 과장·근거 불일치 (수치 진위가 아니라 "근거가 주장을 받치는가")
- **B1 "성공률 유지(V)".** 노트상 Qwen3-32B는 17.0→15.0, Gemini-2.5-Flash-thinking은 40.4→36.4로 떨어졌다. "비용 약 50%↓, 성공률은 대체로 비슷하나 모델에 따라 하락(최대 4%p)"으로 고친다.
- **A5 "Anthropic JSON이 덜 덮어써짐".** 이것은 **모델이 파일을 편집할 때**의 관찰이다. 하네스가 쓰는 블록의 근거가 아니다. "모델은 상태 필드만 바꿀 수 있음"을 유지할 때만 관련이 있다. 그 부분은 B3(모델 메모)과 겹치므로 A5/B0에서 빼고 B3로 합친다. 그러면 상태 블록은 완전히 하네스 작성이 되어 도구도 하나 줄어든다.
- **D1 교사 메모 수치.** 교사는 GPT-5-mini, 학생은 Qwen3-4B이고 AppWorld 결과다. GLM 교사와 사내 업무로의 전이는 (추론)으로 표기한다.
- **D4 SkillsBench.** 측정 모델 규모가 작은 모델과 맞는지 적는다. 노트에 없으면 "(모델 규모 미확인)"으로 표기한다.
- **A1.** "prefix cache 유지"를 "(게이트웨이가 지원할 때)"로 한정한다(M8).
- **A4 근거.** RULER 25~50%와 NoLiMa 약 1K는 "고정 비율이 위험하다"는 근거로는 맞다. 하지만 "실측값을 쓴다"의 실측 방법(C1)은 검증되지 않은 제안(추론)이다. H7의 예측력 검증 전에는 "잠정"으로 표기한다.

### L2. C1 비용 표기
- 길이 6개(64K 포함)의 토큰 합은 1+4+8+16+32+64=125K다. 이것에 과제 4 × 깊이 3 × 5회를 곱하면 약 7.5M이고, 64K를 빼면 약 3.7M이다(검토자 산술. 수치 확정은 사실 검증자 몫).
- 도구 5/15/30개를 길이·깊이와 교차하면 T4가 3배가 되어 360회를 넘는다. 초안 문구로는 교차 여부가 불명확하다. 도구 수 축은 짧은 길이(예: 4K·16K)에서만 돌린다고 적는다.
- 작은 로컬 모델에서 시간을 지배하는 것은 입력 토큰이 아니라 **사고 출력의 디코드**다. 예를 들어 360회 × 사고 1~2K 토큰이고, 느린 디코드 속도에서는 몇 시간이 될 수 있다(추론). "첫 실패 길이 + 1까지만"(노트)의 조기 중단 규칙을 초안에 넣는다.

### L3. A4 필드 성격 구분
- 실측값(`context_tokens`, `effective_ctx`, `chars_per_token`, `probe_date`)과 정책값(`context_tokens_safe`, `max_tool_output`, `keep_last_tool_results`, `max_exposed_tools`)이 한 묶음에 섞여 있다. REPORT 스키마는 "실측으로 채운다, 모르면 null"이 원칙이다. 정책값에는 `*_source: measured|default|manual`을 붙이거나 하위 객체 `policy`로 분리한다. 그래야 probe 재실행이 정책값을 덮어쓰지 않는다.

### L4. C3 요약의 대안 비교
- 작은 창에서 마스킹으로도 예산을 못 맞출 때의 기본 동작이 없다. "예산 소진 → 이유를 기록하고 정상 종료(`budget_exhausted`)"를 기본으로 두고, 요약은 그것보다 나을 때만 켠다(H6 표).

### L5. 기억 오염(D3) 보강
- "검사 통과 사례만 저장"이어도 그 trace 안의 문서 내용(주입된 지시 포함)이 기억으로 옮겨질 수 있다. 다음 세 줄을 D3에 추가한다.
  1. 기억 항목은 사람 또는 교사가 쓴 **요약된 지침**만 허용한다. 도구 출력 원문은 절대 그대로 넣지 않는다.
  2. 프로젝트·사용자별 이름공간을 둔다. 업무 간 기억은 고객 정보의 교차 유출 경로가 된다.
  3. 주입 위치는 첫 user 메시지 안의 "참고 자료(오래됐을 수 있음)" 블록으로 한다. 시스템 역할에는 넣지 않는다(초안 E와 일치).
