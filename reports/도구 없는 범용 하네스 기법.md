# 작은 모델을 키우는 건 싸고 결정적인 하네스다

결론부터 말하면, 업무 전용 도구 없이 작은 모델의 성능을 고르게 올리는 데 근거가 가장 단단한 기법은 모델을 한 번 더 부르는 기법이 아니다. **추가 호출이 0인 결정적 코드**가 근거가 가장 단단하다. 오래된 도구 출력을 잘라 문맥을 정리하고, 같은 행동 반복이나 정체를 감지하고, 오류를 구조화해 돌려주는 기법이 여기에 든다. 셸이나 Python 하나만 주는 범용 행동 공간도 같은 부류다. 같은 모델에서 하네스만 바꿨을 때 5~15%p 차이가 난다는 측정은 2026년에 독립 연구로도 여러 번 나왔다. 그중 작은 문맥 창(20,480토큰)에서는 오래된 도구 출력 자르기와 정체 대응만으로 SWE-bench Verified 과제당 통과 비율이 **28% → 49%**로 올랐다. 반대로 모델이 스스로 다시 검토하게 하는 방식(intrinsic self-correction)은 작은 모델에서 정답을 오답으로 바꿨다. 모델이 직접 만든 스킬, LLM 요약, 다중 에이전트 토론, 그리고 AGENTS.md 같은 규약 파일은 측정에서 이득이 없거나 손해였다. GLM-5.3-Flash와 Qwen3.5-9B에 대한 공개 하네스 측정은 사실상 없다. 그래서 아래 권고는 모두 다른 모델의 결과를 옮겨 온 추론이고, 우리 벤치에서 직접 확인해야 한다. 게이트웨이 429 한도(몇 분에 약 35회)가 있으므로 순서는 이렇다. 먼저 진행 중인 v0 A/B를 끝낸다. 다음으로 호출이 늘지 않는 기법(문맥 정리, `run_python` 단일 행동)을 Qwen으로 먼저 거른다. 호출을 늘리는 기법(다수결, 재시도)은 같은 호출 수 조건에서만 비교한다. GLM으로는 살아남은 한두 개만 확인한다.

## 같은 모델이라도 하네스 차이가 5~15%p를 만든다는 건 이제 독립 근거가 있다

2026년의 큰 흐름은 "모델보다 하네스"다. 다만 숫자마다 출처의 성격이 크게 다르니 구분해서 봐야 한다. 가장 많이 퍼진 사례는 **LangChain Deep Agents(벤더 자체 보고)**다. gpt-5.2-codex를 고정하고 Terminal-Bench 2.0(89과제)에서 하네스만 고쳐 **52.8% → 66.5%**를 얻었다. 하지만 구성 요소별 분리 실험이 없고, 반복 횟수와 신뢰구간도 없다. 저자 스스로 실패 기록(trace)을 보고 고친 변경은 과적합될 수 있다고 경고했다 ([LangChain](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)). **Kimchi(벤더 자체 보고)**는 GLM-5.2를 하네스 네 개로 돌렸다. Terminal-Bench 2.1, 과제당 5회 평균에서 Kimchi 72.6%, Cursor 69.0%, Claude Code 65.4%, OpenCode 59.8%로 13.0%p가 벌어졌다. 분산은 공개하지 않았고, OpenCode 수치는 다른 시기에 돌린 것이라 저자도 "방향성"이라고 했다 ([Kimchi](https://kimchi.dev/blog/same-model-different-harness-terminal-bench)).

독립 학술 근거는 이보다 신중하지만 방향은 같다. 하네스 공개를 요구하는 ICML 2026 입장 논문은 GPT-5.4, Kimi K2.6, GLM-5.1 세 모델에 하네스 세 단계를 곱해 SWE-bench Verified 100과제 부분집합을 2회씩 돌렸다. 하네스를 바꿀 때의 흔들림이 모델을 바꿀 때보다 **7.80배** 컸다. GLM-5.1은 52.5 → 65.5로 올랐고, 순위는 9번 중 6번 뒤집혔다. 저자들은 이 배수가 보편적인 값은 아니라고 밝혔다 ([arXiv 2605.23950](https://arxiv.org/html/2605.23950v1)). NTU 연구는 66개 설정에서 순위 역전을 확인했다. Claude는 OpenHands에서 GPT보다 7.94%p 앞섰지만 PI 하네스에서는 30.16%p 뒤졌다. 이 차이의 상당 부분은 "실패를 모델에게 어떻게 돌려주느냐"에서 나왔다. 다만 과제당 1회만 돌렸고, 회차 간 분산은 재지 않았다 ([arXiv 2610.00917](https://arxiv.org/html/2610.00917v1)). 반면 Terminal-Bench 원 논문은 "대개 모델 선택이 스캐폴드보다 더 중요하다"고 결론 내렸다 ([arXiv 2601.11868](https://arxiv.org/html/2601.11868)). 두 결론은 모순이 아니다. 하네스 효과는 실재하지만, 공개된 숫자 대부분은 1회 실행이거나 벤더가 직접 맞춘 결과다. 우리처럼 사전 등록하고 반복해서 짝 비교하는 시험은 공개된 근거 대부분보다 엄격하다.

작은 모델의 화려한 숫자는 거의 다 벤더가 고른 하네스에서 나왔다. Qwen3.6-27B의 Terminal-Bench 2.0 **59.3**은 벤더 보고다 ([Qwen](https://qwen.ai/blog?id=qwen3.6-27b)). 같은 모델의 SWE-bench Pro 수치는 모델 카드 53.5, bash만 쓴 재현 약 28, `str_replace` 편집 도구를 추가한 재현 50.7이었다는 이야기가 있다. 이 셋은 2차 출처이고 원 GitHub 이슈는 확인하지 못했다 ([AI Realist](https://msukhareva.substack.com/p/how-a-small-open-model-beat-a-frontier)). 우리 사외 모델 Qwen3.5-9B의 Terminal-Bench 2.1 **21.3%**도 출처가 불분명한 벤더 측 수치다 ([Modal](https://modal.com/resources/best-small-open-source-code-llms-ai-agents)). "작은 모델 + 하네스가 프런티어를 이긴다"는 주장은 9B급에서 독립 재현된 적이 없다.

## 추가 호출 없는 문맥 정리와 오류 반환이 가장 단단한 근거를 가졌다

주요 하네스(Codex, Claude Code, OpenHands, Deep Agents)가 공통으로 수렴한 구성은 일곱 가지다. 시작 지시 파일, 할 일 목록, 파일을 외부 기억으로 쓰기, 독립 문맥의 하위 에이전트, 자동 문맥 압축, 호출 전후 훅, 그리고 반복 감지와 종료 전 검증이다 ([OpenHands condenser](https://docs.openhands.dev/sdk/guides/context-condenser); [Claude Code sub-agents](https://code.claude.com/docs/en/sub-agents); [LangChain](https://www.langchain.com/blog/improving-deep-agents-with-harness-engineering)). 이 중 측정으로 이득이 확인된 것은 대부분 LLM을 더 부르지 않는 결정적 코드였다. 표준 라이브러리만으로 만들 수 있는 부분이 바로 그 부분이다.

가장 직접적인 근거는 **"Same Model, Different Harness"(독립 학술, 1저자, 2026년 8월)**다. 대조군은 대화 전체를 그대로 유지했다. 처치군은 문맥이 차면 오래된 도구 결과를 기계적으로 줄이고, 반복되거나 멈춘 작업에 반응했다. 설정은 모델별로 다시 맞추지 않고 고정했다. 문맥 20,480토큰, 시도당 480초 조건의 SWE-bench Verified 169과제에서 과제당 통과 비율 평균이 **28% → 49%**, 완전 해결이 **43 → 72건**으로 늘었다. 같은 고정 처치가 다른 모델 셋에서도 도움이 됐다. 그러나 문맥이 넓은 조건(Qwen3.6)에서는 두 조건이 거의 같았다. 초록에는 반복 실행이나 신뢰구간에 대한 언급이 없다 ([arXiv 2608.26218](https://arxiv.org/abs/2608.26218)). 로컬 9B처럼 문맥이 좁은 환경일수록 이 기법의 이득이 커진다는 뜻이다.

**JetBrains의 "Complexity Trap"(독립 학술, SWE-bench Verified 500과제, ± 보고)**은 값싼 방법이 비싼 방법만큼 좋다는 것을 보였다. 비교한 방법은 둘이다. 관측 가림(observation masking)은 최근 10턴의 도구 출력만 남기고 그 이전 것은 가린다. LLM 요약은 그 이전 부분을 모델에게 요약시킨다. Qwen3-32B는 그대로 17.0±3.3, 가림 15.0, 요약 16.0이었고, 비용은 $1.12에서 각각 $0.55와 $0.50으로 줄었다. 성공률 차이는 통계적으로 유의하지 않았다. Gemini 2.5 Flash thinking에서는 요약이 40.4 → 31.4로 오히려 크게 떨어졌다. 그리고 가림 창 크기는 하네스마다 달랐다. SWE-agent에서는 M=10이 맞았지만 OpenHands에서는 M=58로 다시 맞춰야 했다 ([arXiv 2508.21433](https://arxiv.org/html/2508.21433v3)). 정리하면, 가림은 비용을 절반으로 줄이면서 성공률은 유지하고, 요약은 호출만 더 쓰면서 나을 게 없다.

오류 반환 방식도 결정적 레버다. NTU 연구에서는 OpenHands의 정체 감지기가 회복할 수 있었던 Kimi 실행을 강제로 끝냈다. PI 하네스의 셸에는 기본 타임아웃이 없었다 ([arXiv 2610.00917](https://arxiv.org/html/2610.00917v1)). Terminal-Bench에서 실패의 가장 큰 유형은 설치되지 않았거나 PATH에 없는 실행 파일을 부른 경우로, 실패의 24.1%를 차지했다 ([arXiv 2601.11868](https://arxiv.org/html/2601.11868)). 그러니 반복 감지는 공짜가 아니다. "경고만 주입"과 "강제 종료"를 따로 시험해야 한다. 쓸 수 있는 실행 파일과 모듈 목록을 처음에 알려주는 것도 값싼 대책이다. Kimchi는 벤더 보고로 다음을 개선 요인으로 꼽았다. 가짜 도구 호출과 짝 없는 도구 결과를 메시지에서 정리하는 것, 편집-실행-실패가 반복되면 턴을 끝내는 것, 그리고 GLM-5.2의 "끝없는 사고(unbound thinking)" 문제를 고친 것이다 ([Kimchi](https://kimchi.dev/blog/same-model-different-harness-terminal-bench)). 구성 요소별 분리 실험은 없지만 GLM 계열 고유의 실패라 우리와 관련이 크다.

규약 파일은 반대 사례다. ETH 연구(ICLR 2026, 독립 학술)는 Qwen3-30B 코더 포함 네 조합을 시험했다. AGENTS.md가 없을 때, LLM이 만든 파일, 개발자가 쓴 파일 사이에 정답률 차이가 통계적으로 확인되지 않았다(없음 대 LLM 파일 p=0.87, 0.37). 반면 단계 수와 비용은 약 20~23% 늘었다. Qwen3-30B의 CTXbench 45.7 → 53.6(개발자 파일)이 유일하게 좋아 보이는 신호지만 전체 검정에서 유의하지 않았다 ([arXiv 2602.11988](https://arxiv.org/html/2602.11988v3)). 다른 독립 연구도 288회 실행에서 문맥 전략이 정답률을 "측정 가능하게 움직이지 않는다"고 결론 내렸다 ([arXiv 2607.27250](https://arxiv.org/abs/2607.27250)).

## 업무 도구가 없을 때는 "Python 하나"가 범용 도구가 된다

사용자가 과제 정의 없이 그냥 쓰는 상황에서는 업무별 도구를 미리 만들어 둘 수 없다. 이때 남는 선택지는 셸이나 Python 실행 하나를 주고 나머지를 모델이 코드로 해결하게 하는 범용 행동 공간이다. 작은 모델에 가장 가까운 근거는 아쉽게도 비공식 실험 하나다. **SOTAAZ 블로그(독립 실무자, 2026년 10월, 동료 검토 없음)**의 설정은 이렇다. llama.cpp, Q4_K_M, 온도 0, 사고 끔, 문맥 32K, 답변당 출력 2,048토큰. 가짜 이슈 트래커(이슈 240개, 사용자 30명)에서 정답이 정해진 30과제를 풀게 했다. 비교 대상은 도구 호출 모드(도구 5개, 최대 40회)와 코드 모드(`run_python` 하나, 네트워크·파일 쓰기 금지, 10초 제한, 출력 4,000자에서 자름)였다. **Qwen3.5-9B는 19/30 → 28/30(p=0.012)**으로 올랐고, 둘 다 푼 과제의 토큰 중앙값은 4,003 → 1,787이었다. 차이는 조인·집계 과제(2/10 → 10/10)에서 나왔다. 도구 호출 모드는 손으로 세다가 출력 한도에 걸려 실패했다. 반대로 단순 조회는 4B에서 도구 호출 쪽이 나았다(10 대 7). 한계도 분명하다. 각 1회, n=30이고, 코드 프롬프트가 "코드로 계산하라"고 명시했으며, 채점 관대화를 나중에 추가했다 ([SOTAAZ](https://sotaaz.com/post/codemode-small-models-en)).

다른 근거들은 조건부로 같은 방향을 가리킨다. PwC 저자들의 연구는 폐쇄형 모델 14개를 BFCL v4 309항목 부분집합에서 시험했다. 모델이 Python 스크립트로 도구를 부르게 하자 11개가 JSON 호출과 같거나 나았다. 하지만 GPT-4o는 −26.9, GPT-5.4-mini는 −24.3, GPT-4.1은 −19.8로 크게 떨어졌다. 셋 다 줄바꿈 대신 `\n`을 글자 그대로 써서 문법 오류를 낸 탓이었다. 공개 가중치 모델은 시험하지 않았다 ([arXiv 2608.06370](https://arxiv.org/html/2608.06370v1)). 2024년 CodeAct는 GPT-4에서 74.4% 대 JSON 52.4%를 보였다. 그러나 당시 7B~70B 공개 모델은 형식과 상관없이 0~15.9%였고, Mistral-7B는 코드 0.0 대 JSON 3.7로 코드가 오히려 낮았다 ([arXiv 2402.01030](https://arxiv.org/html/2402.01030v4)). 당시 모델은 지금의 Qwen3.5-9B보다 훨씬 약하므로 예측 근거로 쓰기 어렵다. Vercel 사례(벤더)는 도구 17개를 2개로 줄여 성공률 80% → 100%를 얻었지만 **5개 질의**뿐이었다. 저자도 문서가 이미 잘 정리돼 있었기 때문에 가능했다고 밝혔다 ([Vercel](https://vercel.com/blog/we-removed-80-percent-of-our-agents-tools)).

bash만 쓰는 하네스에는 대가도 있다. SWE-bench 공식 리더보드 데이터에서 같은 공개 모델의 맞춤 도구 하네스 점수와 bash만 쓴 점수를 비교하면 Kimi K2는 65.4 대 43.8, Qwen3-Coder-480B는 69.6 대 55.4다. 다만 날짜와 설정이 달라 통제된 비교는 아니다. GLM 5(high)는 bash만으로 72.8을 냈다. GLM 계열이 bash 규약을 잘 따른다는 신호이지만 GLM-5.3-Flash는 다른 모델이다 ([SWE-bench leaderboards.json](https://raw.githubusercontent.com/SWE-bench/swe-bench.github.io/master/data/leaderboards.json)). 우리 조건에서 구현 자체는 어렵지 않다. `subprocess.run([sys.executable, "-I", ...], timeout=..., cwd=작업폴더)`에 키가 없는 최소 환경변수를 넘기고, 출력은 약 4,000자에서 자른다. 단 이것은 사고 방지 장치일 뿐 보안 경계가 아니다. smolagents 관리자들도 "어떤 로컬 Python 샌드박스도 완전히 안전할 수 없다"고 못 박았다 ([smolagents docs](https://huggingface.co/docs/smolagents/tutorials/secure_code_execution)). Windows 표준 라이브러리에는 `resource` 모듈이 없어서 타임아웃 외의 CPU·메모리 제한에는 ctypes Job Object가 필요하다. 이것은 노트에서 끌어낸 추론이다. 실패 유형에서 나온 값싼 대책도 있다. 코드는 JSON 문자열 대신 코드 블록으로 받는다. 함수의 반환 구조를 프롬프트에 적는다. 최종 답 표시는 강제하되 관대하게 파싱한다.

## 모델을 더 부르는 기법은 외부 신호가 있을 때만 값을 한다

모델 스스로 다시 보게 하는 기법은 작은 모델에서 해롭다. Huang 등(ICLR 2024)의 결과에서 외부 신호 없이 자기 교정을 시키자 Llama-2가 GSM8K에서 **62.0 → 43.5 → 36.5**(1/3/5회 호출), CommonSenseQA에서 64.0 → 36.5로 떨어졌다. GPT-4도 95.5 → 89.0으로 내려갔다. 반면 정답을 알려주고 멈추게 한 경우에는 GPT-3.5가 75.9 → 84.3으로 올랐다 ([arXiv 2310.01798](https://arxiv.org/html/2310.01798v2)). Self-Refine의 약 20% 개선은 GPT-3.5와 GPT-4를 주로 개방형 생성 과제에서 시험한 결과다 ([arXiv 2303.17651](https://arxiv.org/abs/2303.17651)). 우리 v0의 C 조건("다시 확인하고 답해 달라")은 바로 이 내부 교정을 대조군으로 둔 것이다. 반대로 `contract`와 `verify`처럼 구체적 실패 신호를 주는 기능은 근거가 지지하는 쪽이다. 문제는 과제 정의가 없는 사용 상황이다. 과제별 `verify`가 없으니 신호를 범용으로 만들어야 한다. 파싱 오류, 코드 실행 예외, JSON 형식 위반, 사용자가 요청에 적은 형식 조건처럼 과제와 무관하게 기계적으로 잡을 수 있는 신호가 그 후보다.

여러 번 뽑아 고르는 기법은 가장 근거가 많은 기법군이다. 다만 짧고 확인 가능한 답에서만 그렇다. 자기 일관성(여러 번 풀고 다수결)은 GSM8K에서 CoT 대비 +17.9%였다 ([arXiv 2203.11171](https://arxiv.org/abs/2203.11171)). 같은 응답 수를 쓰면 토론보다 나았다. GPT-3.5 GSM8K에서 9응답 기준 다수결 88.2, 토론 83.0이었다 ([arXiv 2310.01798](https://arxiv.org/html/2310.01798v2)). Hugging Face 실험에서는 다수결 이득이 N≈64에서 멈췄다. 1B~3B 모델이 8B~70B를 이긴 결과는 별도의 보상 모델(PRM)로 탐색했을 때 이야기이고, 영역도 수학·코드에 한정됐다 ([HF blog](https://huggingfaceh4-blogpost-scaling-test-time-compute.hf.space/)). 자동 검증기가 없으면 다수결과 보상 모델은 수백 샘플을 넘기면 더 오르지 않는다 ([arXiv 2407.21787](https://arxiv.org/abs/2407.21787)). 우리 환경에서는 비용이 걸림돌이다. 다수결 5회는 호출이 5배라 게이트웨이 한도 안에서 몇 분에 약 7과제밖에 못 돌린다. 로컬 Qwen은 26 tok/s로 1,500토큰 CoT 한 번에 약 1분이 걸려, 5회면 과제당 약 5분이다. 그래서 N=3~5에 "앞의 k개가 같으면 멈춤"을 붙여 짧은 답 과제에서만 쓰는 것이 현실적이다. 이것은 노트의 추론이다.

나머지 기법은 근거가 약하거나 우리 조건과 맞지 않는다. JSON 형식 강제가 추론을 해친다는 주장 ([arXiv 2408.02442](https://arxiv.org/abs/2408.02442))은 Outlines 개발사 dottxt의 재실험에서 반박됐다. 이해관계가 있는 독립 측의 결과로, Llama-3-8B에서 GSM8K 0.77 대 0.78, Last Letter 0.73 대 0.77로 구조화 쪽이 같거나 조금 나았다 ([dottxt](https://blog.dottxt.ai/say-what-you-mean.html)). 요점은 근거 필드를 답 필드보다 앞에 두고, 파싱을 관대하게 하고, 실패할 때만 다시 묻는 것이다. Plan-and-solve와 least-to-most는 2025~2026년에 작은 모델로 통제 실험한 결과를 찾지 못했다. 한 번 호출로 끝나서 싸지만 효과는 미확인이다. 스킬 파일은 갈린다. SkillsBench(독립 학술, v4) 87과제, 18개 설정에서 사람이 쓴 스킬은 평균 통과율을 **33.9% → 50.5%(+16.6%p)**로 올렸다. 모델이 스스로 만든 스킬은 프런티어 모델에서도 **−8.1~−11.5%p**였다. 스킬은 1~3개(+18~19%p)가 4개 이상(+10.1%p)보다 나았고, 짧은 스킬(+19.0%p)이 긴 문서형(+0.7%p)보다 훨씬 나았다. 저자들은 이득 일부가 문맥이 길어진 효과일 수 있다고 했고, 버전 사이에 수치가 바뀌었다 ([arXiv 2602.12670](https://arxiv.org/html/2602.12670)). 도구 자동 생성도 같은 결론이다. 성공 사례는 모두 GPT-4급 이상이 도구를 만들고 실행으로 검증한 경우였다. GPT-3.5는 LATM의 6과제 중 3과제에서 유효한 도구를 0/5개 만들었다 ([arXiv 2305.17126](https://arxiv.org/html/2305.17126v2)). 작은 모델이 실시간으로 도구를 만들게 하는 방식은 근거가 없다. 프롬프트 자동 최적화 GEPA는 Qwen3 8B의 6과제 종합 점수를 45.23 → 54.85로 올렸다 ([arXiv 2507.19457](https://arxiv.org/html/2507.19457v2)). 그러나 과제당 1.8k~7k회를 돌려야 해서 게이트웨이에서는 불가능하다. 사외 Qwen으로 밤새 돌린 뒤 결과 프롬프트를 들고 들어가는 방식만 가능하고, 그 프롬프트가 GLM에도 통하는지는 근거가 없다.

## 도구를 만들어 주는 하네스: 구글 Harness² (2026년 10월)

구글 클라우드 AI 리서치와 노스웨스턴대가 2026년 10월 9일 공개한 Harness²는 "하네스가 과제마다 스스로 하네스를 고친다"는 방향의 대표 사례다. 논문은 arXiv 2610.14224이고, 코드는 github.com/google-research/harness2에 Apache 2.0으로 공개됐다. 구글은 "연구용 코드이며 정식 지원 제품이 아니다"라고 밝혔다.

- **고치는 대상:** 파일로 된 하네스 부품 8가지다. 시스템 프롬프트, 가드레일, 기억, 스킬, 도구 사용 안내, 스크립트, 하위 에이전트, 미들웨어. 과제에 맞춰 스킬과 검증 스크립트를 새로 만들기도 한다. 사실상 "도구를 만들어 주는 하네스"다.
- **누가 고치나:** 편집자 모델이 따로 있다. 기본값은 Claude Opus 4.8(OpenCode 위에서 실행)이다. 실제 일을 하는 모델은 GLM-5와 Gemini 3.5 Flash이고, 가중치는 그대로 둔다.
- **정답 없이 고치는 방법:** 후보 하네스로 같은 과제를 돌려, 원래 하네스로 돌린 결과와 과정·산출물을 비교한다(Propose-Probe-Compose). 저자들도 이 비교는 정답 검증이 아니며 잡음이 있다고 적었다. 벤치마크 점수는 평가에만 썼다.
- **결과** (저자 보고, 과제 순서를 섞어 3회 평균, 한 단계만 고친 경우 / 후보 5개 병렬):

  | 실행 모델 · 기본 하네스 | WorkBuddy | JobBench | LAB |
  |---|---|---|---|
  | GLM-5 · OpenCode | 64.2 → 75.7 / 79.6 | 20.6 → 24.2 / 28.4 | 59.6 → 71.4 / 78.1 |
  | GLM-5 · Codex | 64.4 → 75.3 / 78.3 | 23.6 → 24.8 / 27.9 | 58.1 → 65.9 / 70.7 |
  | Gemini 3.5 Flash · OpenCode | 72.4 → 77.5 / 80.8 | 31.5 → 36.0 / 39.0 | 79.9 → 81.9 / 84.5 |

  과제 수는 WorkBuddy 분야별 40/35/25, JobBench 34, LAB 100이다. 과제당 비용은 본문에서 확인하지 못했다.
- **우리 조건에서의 의미:**
  - 약한 모델일수록 효과가 컸다. 같은 GLM 계열(GLM-5)에서 +7~12점이 나왔다. 앞 절의 "큰 모델이 만들고 작은 모델이 쓴다" 근거와 같은 방향이다.
  - 다만 과제마다 편집자 모델(Opus급)을 실시간으로 불러야 해서, 폐쇄망 안에서 그대로 돌릴 수는 없다.
  - 쓸 수 있는 부분은 하네스 수준의 반복이다. 고친 경험을 다음 과제용 하네스 묶음으로 쌓는 부분이다. 사외에서 강한 편집자로 스킬과 스크립트 묶음을 만들고, 우리 A/B를 통과한 것만 사내로 가져가는 방식이 이것과 맞다.
- **확인하지 못한 것:** 과제당 비용, 한계 부록 전문, 독립 재현 여부.

## 우리 팀의 A/B 순서: 호출 0인 것부터, Qwen으로 거르고 GLM으로 확인

순서를 정한 원칙은 세 가지다. 첫째, 추가 호출이 0이고 독립 근거가 있는 것을 먼저 한다. 둘째, 넓은 후보는 호출 한도가 없는 사외 Qwen3.5-9B에서 3회 반복으로 거르고, 사내 GLM-5.3-Flash에서는 살아남은 한두 개만 B 대 X로 확인한다. 셋째, 호출을 늘리는 기법은 같은 호출 수를 쓰는 대조군(C처럼 턴만 더 주는 조건이나, 같은 횟수의 단순 재시도)과 비교해야 공정하다. 각 단계는 지금 v0처럼 결과를 보기 전에 사전 등록하고, 한 번에 한 요인만 바꾼다. 성공률과 함께 과제당 호출 수와 토큰을 함께 보고한다. GLM과 Qwen의 순위가 조건에 따라 뒤집히는지도 적는다. 이것은 2605.23950이 제안한 보고 방식이다.

| 순서 | 시험 (B 대비 한 요인) | 추가 호출 | 왜 이 순서인가 | 주의할 점 |
|---|---|---|---|---|
| 0 | 진행 중인 v0 A/B(B·C·H) 끝내기 | 기존대로 | 사전 등록이 끝났고, 기능 7개 묶음의 효과부터 확인해야 다음 분해가 의미 있다 | 결과를 본 뒤 과제·채점을 바꾸지 않는다 |
| 1 | 오래된 도구 출력 가림(최근 M턴만 원문 유지) + 정체 시 경고 주입 | 0 (토큰 감소) | 독립 근거 두 편. 좁은 문맥에서 이득이 가장 크다 ([2608.26218](https://arxiv.org/abs/2608.26218), [2508.21433](https://arxiv.org/html/2508.21433v3)) | 지금 과제는 12턴이라 문맥 압박이 약할 수 있다. Qwen 문맥을 좁혀(예: 16~20K) 시험하고, M은 하네스마다 달라서 미리 고정한다 |
| 2 | `run_python` 단일 행동(코드 모드) 대 JSON 도구 호출 | 0 또는 감소 | "도구 없는 사용"의 핵심. Qwen3.5-9B 19→28/30 신호가 있지만 비공식 1회 실험이다 ([SOTAAZ](https://sotaaz.com/post/codemode-small-models-en)) | 코드는 코드 블록으로 받는다(`\n` 오류). 반환 구조와 쓸 수 있는 모듈을 명시한다. 단순 조회는 손해일 수 있으니 과제 유형별로 나눠 본다 |
| 3 | 반복 감지: 경고만 주입 대 강제 종료 | 0 | 회복 가능한 실행을 죽인 사례가 있어서 문턱값 자체가 시험 대상이다 ([2610.00917](https://arxiv.org/html/2610.00917v1)) | 지금 `repeat`은 세 번째에 실행을 막는다. 종료형과 따로 비교한다 |
| 4 | 범용 외부 신호 재시도(파싱·예외·형식 위반 시에만) 대 C(내부 재검토) | 실패할 때만 +1 | 외부 신호가 있으면 돕고 없으면 해친다는 근거가 일관된다 ([2310.01798](https://arxiv.org/html/2310.01798v2)) | 과제별 `verify` 없이 작동하는 신호만 쓴다. 그래야 과제 정의가 없는 사용에도 그대로 옮겨진다 |
| 5 | GLM 전용 메시지 정리(가짜·짝 없는 도구 호출 제거, 사고 길이 상한) | 0 | GLM 계열 고유 실패로 보고됐다(벤더) ([Kimchi](https://kimchi.dev/blog/same-model-different-harness-terminal-bench)) | 사내 실행 기록에서 실제로 나오는 실패인지 먼저 센다. 지금 `recover`와 겹치는 부분이 있다 |
| 6 | 짧은 답 과제 다수결 N=3, 앞의 결과가 일치하면 조기 종료 | ×2~3 | 근거는 강하지만 오래된 대형 모델 기준이고, 호출 비용이 크다 | Qwen에서만 먼저 하고, 같은 호출 수 대조군과 비교한다. GLM은 한도가 허락할 때만 한다 |
| 7 | 사람이 쓴 짧은 스킬 1~3개를 필요할 때 불러오기 | 0 (토큰 증가) | 사람이 쓴 스킬 +16.6%p, 모델이 만든 스킬은 손해 ([2602.12670](https://arxiv.org/html/2602.12670)) | 같은 길이의 무관한 글을 넣은 대조군을 둔다. 스킬은 사외에서 쓰고 리뷰한 뒤 git으로 들여온다 |

뒤로 미루거나 하지 않을 것도 정해 둔다. AGENTS.md식 규약 파일은 비용만 약 20% 늘리고 정답률 근거가 없으니 기본으로 켜지 않는다. LLM 요약 압축, 다중 에이전트 토론, 하위 에이전트, 모델이 실시간으로 도구나 스킬을 만드는 기능은 모두 호출을 늘리면서 작은 모델에서 근거가 없거나 음수다. 그래서 위 순서가 끝난 뒤에 다시 검토한다. GEPA 같은 오프라인 최적화는 사외 Qwen으로 밤새 돌릴 수 있지만, GLM으로 옮겨지는지 별도 A/B가 필요하다. 게이트웨이 쪽에서는 이미 들어간 `LLM_GAP` 간격과 429 재시도를 유지한다. 429로 끝난 실행은 사전 등록 규칙대로 인프라 오류로 빼고 건수를 보고한다.

## 결론

이번 조사로 질문의 형태가 바뀌었다. "어떤 똑똑한 기법을 더할까"가 아니라 "모델에게 보여주는 것과 돌려주는 것을 얼마나 깨끗하게 만들까"가 작은 모델 하네스의 중심이다. 근거가 단단한 기법은 거의 모두 결정적 코드였다. 오래된 출력을 가리고, 타임아웃을 걸고, 오류를 구조화해서 돌려주고, 행동 공간을 Python 하나로 줄이는 것이다. 이것은 표준 라이브러리만 쓰는 폐쇄망 하네스와 429 한도에 우연히도 가장 잘 맞는 부류다. 반대로 호출을 늘리는 기법은 외부 검증 신호가 있을 때만 값을 하는데, 과제 정의가 없는 사용에서는 그 신호가 가장 부족하다. 그래서 "과제와 무관하게 기계적으로 잡을 수 있는 실패 신호"를 얼마나 만들어 내느냐가 범용 하네스의 실질적인 경쟁력이 된다.

마지막으로 GLM-5.3-Flash와 Qwen3.5-9B에 대한 공개 측정은 사실상 비어 있다. 우리 사전 등록 A/B 결과는 내부 판단 근거이면서, 같은 질문에 대한 외부의 몇 안 되는 엄격한 데이터가 될 수 있다. 팀 자산으로서는 결과표에 하네스 설정(문맥 창, 출력 자르기, 반복 감지 문턱값, 호출 수)을 함께 남기는 습관이 개별 기법 하나보다 오래 남는다.
